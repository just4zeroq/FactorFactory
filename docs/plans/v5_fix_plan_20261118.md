## 0. 判断与边界

**主链路逻辑自洽**：S0–S7 八工位 + 十二能力的调用协议、指纹链、权限分区、fail-closed 风格是这套代码里质量最高的部分。没有发现**污染收益方向**的算式错误。

问题集中在四类边界：

| 类别 | 特征 | 危害形式 |
|---|---|---|
| **对账类字段用错公式/漏白名单** | 名字声称 A，值其实是 B | 事后无法复现、无法对账，但**当期不报错** |
| **两条并行实现分叉** | ops 版 vs engine 版、fit/generate vs build | 同一语义两个结果，取决于谁被调用 |
| **设施/字段建了没接** | cache、digest_svc、stateful 标志、fitted_state_ref | "看起来支持"，实际死代码 |
| **判重只做到身份层** | AST 相同才算重复 | `n_trials` 虚高 → DSR 门槛被自己收紧 |

修复原则（沿用既往裁决）：
1. **判据只收紧不放宽**。`dsr_min` / `fdr_max` / `n_trials` 不动；重复检测带来的 `n_effective_trials` 只作诊断落盘。
2. **契约演进先改文档再改代码**。凡涉及 `reason_codes`、`params` 新键、新输出字段的，先改 `docs/` 对应篇目，再改实现。
3. **一个语义一套实现**。发现两套就归一，不保留"并行正确"。
4. **每批独立可验收**，跑 `venv/Scripts/python.exe -m pytest tests/v5 -q` 全绿才进下一批。

## A 组 · 对账与契约正确性（P0，共 5 项，改动量都在 10 行内）

> 这组不改变任何数值结果，只让"落盘的指纹/索引/校验"名副其实。收益/成本比最高，排第一。

### A1 `certify` 的 `policy_digest` 不是 policy_digest
- 位置：`capability/ops/certify.py:258`
- 现状：`compute_digest({"kind": "certify_policy_view", "view": ...})`
- 本体：`contracts/digest.py` 的 `policy_digest(kind, baseline, constitutive, caliber, domain)` → `H({"kind":"policy", ...})`
- 后果：名字叫口径指纹，值是另一套哈希。`reproducible_manifest` 声称可复现，但**永远无法与 ticket 的 `policy_digest` 对上**。
- 改法（二选一）：
  - (a) 改名 `policy_view_digest`，并在 `reproducible_manifest` 里**另加**真正的 `policy_digest`（推荐：信息量不减，且能与 ticket 对账）
  - (b) 直接换成 `digest.policy_digest(...)` —— 需要 certify 持有 baseline/constitutive，检查是否拿得到
- 验证：新增断言 `cert.payload["reproducible_manifest"]["policy_digest"] == ticket.policy_digest`

### A2 索引的 kind 白名单漏 `parcel_data`，与 GC 分叉
- 位置：`storage/index.py:86`（5 类）vs `storage/gc.py:31`（6 类，含 `parcel_data`）
- 后果：`parcel_data` 对象永不进 `db/meta.duckdb`、永不受 `assert_consistent` 覆盖；GC 认为它是活对象、索引认为它不存在。
- 改法：抽出唯一白名单常量（放进 `storage/layout.py`，与 `layout.fact_kind()` 同源），index 与 gc 都引用；**禁止各写一份元组**。
- 验证：`tests/v5` 加一条 "每个 `layout.FACT_KINDS` 成员都被 index 的 `_rebuild_object_rows` 覆盖"

### A3 `_collect_params` 漏 `portfolio` 与 `allocate`
- 位置：`contracts/plan_schema.py:223`
- 现状：只收 `boundary / panel / target / evidence / certify / verdict / search.algorithms[*]`
- 后果：`portfolio.params` 或 `allocate.params` 里写 `cost_tiers` / `embargo` / `rebalance` 这类口径字段，`_check_caliber_leak`（E1020）**看不见** → 口径合法地存在两份，且互不报错。
- 改法：把工位元组改成从 `plan_schema.root` 的键里派生（`boundary/panel/target/search/evidence/verdict/portfolio/certify/allocate`），`search` 单独处理 `algorithms[*]`。
- 验证：构造一份 `portfolio.params.cost_tiers` 的 plan，断言抛 E1020。

### A4 portfolio 窗口隔离用错错误码（E1008 → E1021）
- 位置：`contracts/plan_schema.py` 的 `cross_field` X6（`"code": "E1008"`）vs `capability/ops/combine.py::_check_window`（E1021）
- 文档：`docs/18-plan-schema.md:219` 明确 X6 = **E1021**；`s0/03-runtime.md:314` C21 同。
- 后果：同一约束在编译期报 E1008（通用参数非法），在运行期报 E1021（三段窗口非法）。调用方按码分支处理时会漏。
- 改法：`plan_schema.json` 的 X6 码改为 E1021；X4/X5/X7 一并核对该不该是 E1008（X4/X5 是缺字段，E1008 合理；X7 是区间关系，应为 E1021）。
- 验证：`_check_cross_field` 单测断言 code。

### A5 `ledger.append` 锁内重扫不回并实例视图
- 位置：`storage/ledger.py:72-89`
- 现状：进锁后重扫磁盘得到 `seen`，只用它判断本次是否重复；`self._seen` 只 add 本次新 key，不并入重扫结果。
- 后果：同进程内另一实例写入的记录，本实例 `_seen` 里没有；下次 `append` 仍会重扫（所以**不会写重**），但任何依赖 `_seen` 做"已存在"判断的路径会误判。
- 改法：`self._seen = set(seen) | self._seen`（或 `self._seen |= seen`）。
- 附带：`count()` 每次全量读文件（O(n)），改为 `len(self._seen)` 或维护计数器；若要求与磁盘严格一致，则保留但加注释说明成本。
- 验证：两实例交叉 append 同一 event_id，断言文件只有 1 行且两实例 `count()` 一致。

## B 组 · 回测与成本口径（P0/P1，影响数字）

### B1 `_price_frame` 要求全量有限正数 —— 扩标的必炸
- 位置：`capability/backtest_engine.py:138`
- 现状：`if not np.isfinite(price).all() or np.any(price <= 0.0): raise E3003`
- 对比：`capability/ops/backtest.py:241` 是容忍 NaN（缺失 → 当期收益 0）
- 后果：当前 20 永续面板完整所以没暴露；**一旦加入未上市/停牌/退市标的，整条回测直接失败**，而这是"扩标的"这一既定方向的必经之路。
- 改法（二选一，需拍板）：
  - (a) 允许 NaN：缺失格不建价、当日该标的不成交，权重按剩余成员重归一并记入 `dropped_bars.by_reason["missing_price"]`。这是正确语义，但要改 `_fill_weights` 与 ledger 生成路径。
  - (b) 保持 fail-closed，但在上游 Boundary 显式产出 `tradable_mask` 并把 NaN 处的权重置 0，然后 **price 用前值填充后传入**，并在 `caliber` 里声明填充规则。
- 推荐 (a)。(b) 会把"填充"藏进编排层，与"不填充"的全局约束（`stats.py` 模块 docstring）冲突。
- 验证：造一个含 NaN 列的面板，断言回测成功且缺失期该标的权重为 0。

### B2 `ops/backtest.py` 的四项保证金口径字段完全未消费
- 位置：`capability/ops/backtest.py:315-318`（校验 `max_leverage / initial_margin / maintenance_margin / liquidation_buffer`）→ 计算里一个都没用；`backtest_engine.py:204-231` 才真用
- 后果：向量化版是"看起来支持杠杆与强平"的假实现。它目前只被单测当夹具，但一旦有人拿它出数，会得到**无强平、无保证金**的回测，且 `declared` 口径与实际不符。
- 改法（需拍板）：
  - (a) 删除 `ops/backtest.py` 的 `build`，单测改用 engine 版的小样本夹具
  - (b) 保留但在模块 docstring 顶部与 `outputs` 里显式标 `liquidation_supported: false`，并对非 1 倍杠杆直接 E1004
- 推荐 (b)：成本最低、不破坏现有测试；同时把"capability 层不允许有两套回测语义"写进待办。
- 验证：传 `max_leverage=3` 给 ops 版，断言抛 E1004（而非静默忽略）。

### B3 滑点口径不可配置 —— `caliber.net` 写不出真值
- 位置：`capability/ops/backtest.py:265`、`capability/backtest_engine.py:171-173`
- 现状：滑点一律取 `fee / 2`（`fixed` 档取最低档的一半）；`caliber.net` 里没有任何字段能表达"滑点 = 1bp"。
- 后果：净收益数值被一个隐式假设决定，且该假设无法从 plan 里读出、无法写进报告、无法在成本敏感度曲线里扫描。
- 改法：`caliber.net` 增 `slippage: {mode: enum{fee_fraction, bps, fixed}, value: float}`，
  `fee_fraction` 的 `value` 即当前 `0.5`（默认值，保持向后兼容）。这是契约新增，需先改 `docs/s0/02-caliber.md` + `plan_schema.json`。
- 验证：同一份计划分别设 `slippage={mode: bps, value: 1}` 与 `{mode: fee_fraction, value: 0.5}`，断言 `cost_breakdown.slippage` 不同且与手算一致。

### B4 `backtest_engine` 的行情帧是"伪 OHLCV"
- 位置：`capability/backtest_engine.py:145-148`
- 现状：`open = high = low = close = px`，`volume = 1000.0`（常量）
- 后果：① ml4t 的 `partial_fills_allowed=True` 实际不受任何约束（成交量恒定且永远够）；② 无法做 VWAP/限价成交模拟；③ `long_short_split` 与 `attribution` 的成交归因只能到合成价。
- 也是 `symbols = tuple(f"A{j}" ...)`（`:216`）的同类问题：真实标的名被丢弃，归因无法回溯。
- 改法：`build` 的 inputs 增可选 `volume` / `symbols`（缺省沿用当前合成值，并落 `assumptions` 字段声明"合成行情"）；`_price_frame` 透传真实 symbol。这是**新增可选输入**，不破坏现有调用。
- 验证：传真实 symbols，断言 `fills` 的 asset 列是真名。

### B5 `gross_bar` 尾部补 0 无断言
- 位置：`capability/backtest_engine.py`（`np.pad(gross_bar, (0, t_len - len))`）
- 现状：若 ml4t 返回行数少于 `t_len`，尾部补 0 并继续；若多于 `t_len`，靠切片截断（不报错）。
- 后果：ml4t 版本升级改变行数语义时，会**静默产出错位的净值曲线**——最严重的一类 bug（数值看着正常，只是年月对不上）。
- 改法：取回后断言 `len(gross_bar) == t_len`，不等则 E3003 并打印双方长度。
- 验证：mock 一个长度不符的返回，断言 E3003。

**缺的两层：**

**C1 · 经济等价判重（根因）**
`mean(close,5)` 与 `mul(mean(close,5),1.0)`、`rank(x)` 与已 rank 过的 x —— AST 不同 → `candidate_id` 不同 → **各计一次 trial**。
后果不是"多几个候选"，而是 `n_trials` 虚高 → `expected_max_sr = σ·√(2ln n)` 上升 → **自己把 DSR 门槛收得比真实试验数更严**。
> 注意：这正是不能用"清空 n_trials"来修的那类问题（记忆中的明令禁止项）。正确做法是**另记一个 `n_effective_trials`**，两个数都落盘，判据仍用保守的 `n_trials`。

**C2 · 判重位置偏后**
相关性剪枝只在 Portfolio、且默认关。100 个 `mom60` 变体会完整走完 Evidence → Verdict → 全部进 BH 族，组合阶段才可能被剪。
数据在 **Evidence 出分之后**就已齐备（每个候选的 `values` 数组都在），那里是判重的自然位置。

### C3 实施方案：Evidence 层加"相关性聚类 + 代表性标记"

**为什么不放 Search / 不放新工位**
- Search 内剪枝：那时只看到部分候选，且剪掉会**污染 `n_trials` 记账**（被剪的不该算没试过）。
- 新增第 9 工位：破坏"固定八工位"不变式，代价远大于收益。
- Evidence 是唯一同时满足"已见全体候选 + 已有 score 矩阵 + 尚未进入判据"的位置。

**改造点（`capability/ops/observe.py`）**

1. 循环内保留 `values`：`values_store.append((cid, values))`（当前循环结束即丢弃）
2. 循环后新增 `_redundancy(values_store, tau, rep_key)`：
   - 两两算 `stats.row_corr(a, b, method="spearman")` 的逐时点均值 → `ρ_ij`
   - 只对 `stage_a_pass=True` 的候选计算（数量少，且未过筛的本就不进判据）
   - 贪心聚类：按 `|ic|` 降序遍历，与任一簇代表 `|ρ| >= tau` 则入该簇，否则自立为代表
   - 输出：`{"threshold": tau, "method": "spearman", "n_effective": 簇数, "clusters": [{rep, members, min_abs_corr}], "max_pair_corr": ρ_max}`
3. 回填每个候选：`metrics["redundant_of"] = rep_id or None`
4. 顶层输出增 `"redundancy": {...}`（`outputs` 从 2 键变 3 键，见 C4 契约变更）

**Verdict 侧（`capability/ops/verdict.py`）**

5. 新增 `reason_code: "redundant"`（**必须先改文档**，见 C4）
   - `redundant_of is not None` → `decision = "watch"`，`reasons = ["redundant"]`
   - **不是 reject**：它是真信号，只是不独立；reject 会污染 `family` 的失败计数
6. `statistics` 增 `n_effective_trials`（从 `observation_set.redundancy.n_effective` 读）
7. **判据门槛仍用 `n_trials`**，`n_effective_trials` 只落盘。理由：用 n_effective 会放宽 `expected_max_sr`，属于"下调判据"红线。

**参数出口（`capability/registry/params.json` 的 `observe.params`）**

8. 新增
```json
"dedup": {
  "type": "map", "required": false,
  "keys": {
    "corr":      {"type": "float", "required": false, "ge": 0, "le": 1},
    "method":    {"type": "enum",  "required": false, "values": ["spearman", "pearson"]},
    "rep_by":    {"type": "enum",  "required": false, "values": ["abs_ic", "hac_t", "abs_gross_sharpe"]}
  }
}
```
9. 缺省 `corr = 1.0`（关闭）→ **零破坏**，现有 7 份 plan 行为不变
10. 建议生产值 `corr = 0.9`，在 `examples/` 里给一份开启的样例

**契约变更清单（需先改文档）**

| 文件 | 变更 |
|---|---|
| `docs/s0/04-capability.md:409` | `reason_codes` 增 `redundant`（现冻结 5 个） |
| `s0/04-capability.md` §3.6 | `observe` 返回增 `redundancy`；`per_candidate[*].metrics` 增 `redundant_of` |
| `18-plan-schema.md` | `evidence.params` 增 `dedup` 子块 |

| `ACCEPTANCE.md` | 新增 AC：构造 3 个 `|ρ|>0.9` 的候选，断言 `n_effective=1`、2 个 `watch/redundant`、`n_trials` 不变 |

## D 组 · 评估指标补全（P1）

### D1 `ic` 名不副实 —— 只有 Spearman，没有 Pearson
- 位置：`capability/inference.py:52` `ic_series` 只做 Spearman；`observe.py:358` 注释自认 `rank_ic` 与 `ic` 同源
- 后果：无法判断"信号是否线性"，只能判断"秩是否单调"。对做权重（`score_weighted`/`fixed_ridge`）的因子，线性性是关键。
- 改法：`ic_series(..., method="pearson")` 增参；`metrics` 增 `pearson_ic`；`params.json` 的 `metrics.enum` 扩 `pearson_ic`。**保留 `ic` = Spearman 不动**（改语义会破坏历史对比）。
- 验证：构造 `y = x^3` 的样本，断言 `pearson_ic > 0.9` 而 `rank_ic ≈ 1` 但两者数值不同。

### D2 分组单调性（quintile / tercile）
- 现状：完全没有。IC 高不等于分组收益单调，非线性因子会在 IC 上"及格"而在多空组合上失效。
- 改法：`observe` 增 `group_returns`（按 score 分 5 组，逐期等权收益均值），`metrics` 增 `monotonicity`（组序与收益序的 Spearman）。
- 依赖 `stats.cs_rank`（已有）。

### D3 DSR 的偏度/峰度恒为空转
- 位置：`verdict.py:319` 读 `net_skew` / `net_kurtosis`；**全仓无产出方**
- 后果：DSR 恒按正态 `(0, 3)` 算。加密日频收益的肥尾是 DSR 最该修正的地方，修正项名义存在、实际未生效。
- 改法：`observe._longshort` 已有多空序列 `ls`，直接 `scipy.stats.skew(ls)` / `kurtosis(ls, fisher=False)` 填进 metrics。两行。
- 验证：构造肥尾序列，断言 `net_kurtosis > 3` 且 DSR 与正态假设下的值不同。

### D4 IC 衰减曲线
- 同一因子在 `h ∈ {1, 5, 10, 20}` 上的 IC。成本/换手取舍只能靠它定。
- 改法：`observe` 增可选 `ic_decay: list[int]`，对每个 h 重算 `forward_return` + `ic`。开销 ×len(h)。

### D5 `verdict` 的 `ir`/`n_obs` 回落分支是死代码
- 位置：`verdict.py:309`（`sr is None → 读 ir/n_obs`）；全仓无 `ir`/`n_obs` 产出方
- 改法：删除该分支 + `_REQUIRED_METRICS` 里相关项；或标注 `# V4 兼容，当前无生产方`。

## 执行顺序（每批独立验收）

```
A（5 项，纯对账，半天）
  └─→ C（判重专项，含契约变更，1–2 天）
        └─→ D1+D3（Pearson IC + 填 skew/kurt，直接影响判据质量，半天）
              └─→ B3（滑点出口化，影响净收益数值，需契约变更，1 天）
                    └─→ B1+B4+B5（回测契约，为扩标的铺路，1–2 天）
                          └─→ F2（序列化固定，防指纹漂移，2 小时）
                                └─→ E（纯清理，可随时插入，1 天）
                                      └─→ G（硬编码，按需，2 天）
```

**理由：**
- A 排第一：零风险、纯对账、先让"可复现"这条声明成立。
- C 排第二：契约变更要动文档，越早越好；且它决定后续所有 `n_trials` 相关数字的可信度。
- B3 在 B1 之前：滑点先出口化，B1 改价格容错时才能顺手把"缺失期成本"算对。
- E/G 最后：纯清理，不改变行为，插在任意两批之间跑测试即可。

**回归门槛（每批必过）：**
1. `venv/Scripts/python.exe -m pytest tests/v5 -q` 全绿（当前基线 697）
2. 至少一条真实五跑复跑，指纹逐位一致（排除该批有意变更的指纹）
3. 涉及数值的批次（B/D）加一份"旧值 vs 新值"对照，写进 `docs/reviews/stage/`

## 需拍板的决策

### 决策 1 · `n_effective_trials` 要不要进判据？
- **选项 A（推荐）**：只落盘为诊断，DSR/FDR 仍用 `n_trials`。保守，不触碰"永不放宽判据"红线。
- 选项 B：DSR 用 `n_effective_trials`。更"数学正确"，但会让门槛下降 `√(ln n_eff / ln n)`，等于放宽。
- 建议先 A 跑 3–5 次真实搜索，看 `n_effective / n_trials` 的实际比值，再决定 B 是否值得。

### 决策 2 · `redundant` 候选给 `watch` 还是 `reject`？
- **选项 A（推荐）**：`watch`。它是真信号，只是不独立；`reject` 会污染族失败计数，且会让"同一因子换个名字重跑"永远无法通过。
- 选项 B：`reject`。语义更干脆，但与"拒绝重复"的初衷相反（重复不等于无效）。

### 决策 3 · `ops/backtest.py` 留还是删？
- **选项 A（推荐）**：留 + 显式降级（`liquidation_supported: false`，杠杆≠1 直接 E1004）。
- 选项 B：删。单测需换夹具，风险中等。

### 决策 4 · `parcel_data` 进不进索引？
- **选项 A（推荐）**：进。GC 与索引同源，"谁算活对象"只能有一个答案。
- 选项 B：不进，从 `gc._KINDS` 删掉。那 `parcel_data` 就完全脱离回收与一致性视图，需在文档里声明。

### 决策 5 · 缓存接不接？
- **选项 A（推荐）**：本轮不接，把 F5/F6 从 S6 验收口径划掉（写进 `ACCEPTANCE.md` 的"未覆盖"栏）。
- 选项 B：接。改动 `_invoke_station` / `_persist`，且会破坏"每次全量重算"的可复现假设，需单独一批 + 新 AC。
