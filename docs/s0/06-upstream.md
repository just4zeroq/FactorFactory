# S0 · 06 流水线之外

> **已被 `../19-supply.md` 取代（2026-11-17）。** 本文保留作为设计推导的历史记录：
> 它回答了「为什么供给必须在流水线之外」，但 §3–§7 的**事务协议**（暂存 → 定稿 →
> 门禁 → 登记 → 别名，配租约与维护日志）已判定为对单机批量研究过重，改为
> 「一份数据集 = 一组 parquet + 读取时现算身份」。**§1 的边界判据与 §8 的 A/B 分工仍然有效。**

> 这一层不产生执行、不进状态机、不写执行记录。它的唯一职责是把「外部世界」变成「不可变的事实版本」。
> 它不是第五个工位，而是**一个独立的写者**：唯一有权写共享仓的角色。

---

## 1. 边界判据

> 流水线只做「事实 → 结论」的确定性变换；任何「外部世界 → 事实」的动作都在流水线之外。

按这条判据归类，与有没有网络无关：

| 属于维护链 | 不属于维护链 |
|---|---|
| 交易所行情采集 | 面板对齐 |
| 退市公告抓取 | 标签生成 |
| 人工标注存续表 | 因子计算 |
| 字段规范化与单位换算 | 成本模型 |
| 上游数据修订的重新拉取 | 缓存重建 |

分界线是**是否产生新的外部事实**，不是计算量大小。面板对齐可能很重，但它的输入全在仓里，可以确定性重算，所以属于流水线内部。

### 1.1 它不是「第零工位」的理由

| 工位契约 | 采集的实际行为 |
|---|---|
| 给定冻结输入，确定性算出产物 | 产出**输入本身** |
| 可重复，同输入同输出 | 依赖网络时点，同请求可能不同结果 |
| 失败即失败，重跑确定 | 限流、超时、部分成功、上游修订、断点续传 |
| 写自己的工位目录 | 写共享仓，并被所有执行读 |

四条没有一条成立。把它塞进状态机，就要给其余七个工位引入一整套用不上的外部 IO 语义。

## 2. 命令面

```
supply acquire --dataset <name> [--since <t>] [--until <t>] [--resume]
supply verify  --dataset <name> --version <v>
supply publish --dataset <name> --version <v> [--dry-run]
supply status  [--dataset <name>]
supply gc      --derived [--keep <n>]
```

| 命令 | 是否写 Depot | 是否移动别名 | 说明 |
|---|---|---|---|
| `acquire` | 只写 `staging/` | 否 | 采集到暂存，不发布 |
| `verify` | 否 | 否 | 重算校验和、复查门禁 A |
| `publish` | 是（staging → seeds） | **是** | 原子发布 + 移动别名 |
| `status` | 否 | 否 | 版本列表、别名指向、门禁结果 |
| `gc` | 是（仅 Derived） | 否 | 清理可重建派生物 |

`acquire` 与 `publish` **必须分开**。合并成一个命令，就会出现「采集成功但校验失败」时别名已被移动的窗口；分开之后，别名只在门禁通过后才移动，且这个动作是唯一可回滚点（回滚 = 指回旧版本）。

三条禁止：

1. `acquire` 不得移动别名；
2. `publish` 不得触发采集（缺数据就失败）；
3. 任何 `supply` 命令都不得写 `Ticket/`。

## 3. 门禁 A：完整性

采集侧判定，**决定一个版本能不能被发布**。

| 检查 | 判据 | 失败码 |
|---|---|---|
| 覆盖区间 | 实际覆盖 ⊇ 请求区间；缺口必须显式列出 | `E4002` |
| 标的集 | 实际标的 ⊇ 请求标的；缺失逐个列出 | `E4002` |
| 校验和 | 重算与清单一致 | `E4004` |
| 末端闭合 | 时间末端无未完成 bar | `E4003` |
| 字段完整 | 每个标的的字段集一致，无整列为空 | `E1014` |
| 时间单调 | 时间索引无重复、无逆序 | `E4007` |
| 上游修订 | 与同名旧版本比对，标记新增/修订区间 | 不失败，记 `revision_detected` |

门禁 A **不通过**的版本：可以保留在 `seeds/`（供排查），但

- 不得被 `pins/` 指向（`E4005`）；
- `manifest.gate_a.passed = false` 且带 `reason_code`；
- `supply status` 必须显示为「已存在但不可用」。

保留而不是删除，是因为「为什么这份数据不能用」本身需要证据。但如果它被别名指向，整套 PIT 保证就作废了。

## 4. 原子发布协议

五个阶段，任一阶段失败都不得留下「别名指向半成品」的状态。

| 阶段 | 动作 | 失败处理 |
|---|---|---|
| 1 暂存 | 写入 `upkeep/staging/<dataset>/<version>/` | 保留暂存，可 `--resume` |
| 2 校验 | 重算校验和、查清单完整性 | 保留暂存，记失败 |
| 3 门禁 A | 七项检查 | 保留暂存，记失败 |
| 4 登记 | 移动到 `seeds/<dataset>/<version>/`，写 `manifest.json` | 回滚移动 |
| 5 移动别名 | 写临时文件 → `rename` 到 `pins/<dataset>.json` | 保持旧别名 |

第 5 步的原子性只能靠**同分区内 `rename`**：先写 `pins/.tmp-<uuid>`，再 `rename` 覆盖。直接写目标文件会产生「读到半个 JSON」的窗口。

第 4 步与第 5 步之间是唯一的不一致窗口：版本已存在但别名未移动。这个窗口是安全的——它表现为「新版本可用但未被使用」，而不是「别名指向不完整数据」。

**阶段 2 还必须核对「暂存是不是本次请求的产物」**：manifest 的 `dataset` / `version` /
`timeframe` / `fields` / `exchange` 与请求逐项比对，任一不符即 `E4004`。只比
`dataset` / `version` 不够——目录名是内容指纹，手工塞入另一请求（不同频率或另一
交易所）的暂存时，门禁 A 会用**本次** request 的 delta 去算覆盖与闭合，得到
「看似通过」的结论。`exchange` 进 manifest（不进 `Pin`：九字段冻结），是
「这份 payload 从哪个交易所来」的唯一审计依据；V4 曾因 `exchange_id` 被改写而
把数据写进错目录。

**定稿顺序固定为「同步 manifest.version → rename → 迁移维护日志」**。rename 之后
「目录名 == manifest.version」恒成立；rename 之前被 kill 只会留下 `version != 目录名`
的暂存，`--resume` 判定不可复用并清掉重拉。反过来（先 rename 再改 manifest）会留下
一个既不能复用、又过不了发布校验的中间态，`--resume` 每次重跑都失败。

### 4.1 幂等

| 情形 | 行为 |
|---|---|
| 同 `version` 已存在且校验和相同 | 不重写、不改 `acquired_at`、只追加一条维护日志 |
| 同 `version` 已存在但校验和不同 | `E4004`。内容寻址下这不可能发生；发生时说明有内容损坏 |
| 不同 `version` | 正常发布，旧版本保留 |

### 4.2 上游修订

同一区间重新采集得到不同内容，是**正常现象**，不是错误：

- 产生新 `version`（内容寻址天然如此）；
- 维护日志记 `revision_detected` 与差异区间；
- 旧版本继续可读，旧执行继续可复现；
- 别名移动后，新执行的 `pin` 变，`Panel` 起 `stale`，但**不新建试验族**（事实演进不是研究自由度）。

## 5. 租约

同一数据集同时只允许一个写者。

```
Depot/upkeep/leases/<dataset>.lock
  { lease_id, owner, host, pid, acquired_at, expires_at }
```

| 规则 | 内容 |
|---|---|
| 获取 | 文件不存在则创建；存在且未过期 → `E5002` |
| 续期 | 采集过程中按心跳续期 |
| 过期 | 超过 `expires_at` 视为失效，可被抢占 |
| 抢占 | 必须记录 `previous_owner` 与 `reason=expired`，并留下日志 |
| 释放 | 正常结束或异常退出都要释放；异常退出靠过期兜底 |

租约不是性能优化，是正确性要求：两个写者同时移动别名，最终指向哪个版本无法解释。

## 6. 维护日志

`Depot/upkeep/log/<dataset>/<version>.jsonl`，只追加。

| 字段 | 说明 |
|---|---|
| `ts` | UTC |
| `dataset` / `version` | |
| `action` | `acquire` / `verify` / `publish` / `gc` / `lease` |
| `result` | `ok` / `failed` / `partial` |
| `lease_id` | 关联键 |
| `detail` | 结构化，如缺口区间、标的数、耗时 |
| `error_code` | 失败时必填 |

三条规则：

1. **不属于任何执行**。维护日志出现在 `Ticket/` 下即 `E5005`。
2. **不含凭据**。`detail` 里的源地址可以记录，令牌不行。
3. **可反查**。执行侧通过 `pin.version` 能定位到对应维护日志；这是「两套日志」问题的唯一缓解手段。

## 7. 失败语义

| 情形 | 版本是否保留 | `gate_a.passed` | 别名 | 退出码 |
|---|---|---|---|---|
| 鉴权失败 | 否 | — | 不动 | 4 |
| 网络中断（部分） | 是（暂存） | `false` / `partial` | 不动 | 4 |
| 限流 | 是（暂存，可续） | `false` | 不动 | 4 |
| 校验和不符 | 是 | `false` | 不动 | 4 |
| 末端未闭合 | 是 | `false` | 不动 | 4 |
| 上游修订 | 是（新版本） | `true` | **移动** | 0 |
| 租约冲突 | 否 | — | 不动 | 1 |
| 磁盘满 | 否 | — | 不动 | 1 |

关键区分：**「不可用」与「失败」不是一回事**。不可用的版本可以存在（供排查），但绝不能被使用。把两者混为一谈，就会出现「为了让流程走下去，把不完整版本发布出去」。

### 7.1 部分成功的处理

部分成功必须走三条：

1. `manifest.missing_ranges` 显式列出缺口；
2. `gate_a.passed = false`，`reason_code = incomplete_coverage`；
3. 退出码 4（不是 0，也不是 2）。

**不得**把「拿到了 90% 的数据」当作成功并静默缩短研究窗口。研究窗口由计划声明，不由数据可用性倒推。

## 8. 与门禁 B 的边界

| | 门禁 A | 门禁 B |
|---|---|---|
| 归属 | 采集侧 | 编译侧 |
| 写权限 | 写 Depot | **只读** |
| 回答 | 这份事实完整吗 | 这份事实能回答**本次**问题吗 |
| 失败 | 版本保留但不发布 | FATAL，不创建执行 |
| 能否补救 | 重新采集 | 提示先做维护，**自己不补** |

两个门禁不能合并：A 是「对世界」的判断，B 是「对这一个问题」的判断。同一份数据对研究 A 足够、对研究 B 不够，合并就没法表达。

**门禁 B 绝不自动补采**，这条是硬性的。编译期产生副作用会让「编译前」和「编译后」的 Depot 状态不同，版本可能在编译中途变化。

---

## 9. 与执行的关系

| 关系 | 规则 |
|---|---|
| 时序 | 维护必须发生在编译**之前**；编译只能读已发布版本 |
| 触发 | 维护**不得**被编译、单步、恢复、认证触发（`E4006`） |
| 失败传播 | 维护失败不写任何执行状态，不改变任何已归档结论 |
| 外层调度 | 允许一个组合命令按「维护 → 编译 → 执行」串起来，但三者仍是三个独立步骤，成败分开记录 |

外层调度是纪律工具，不是新的层。它可以让「每次都用最新事实」成为默认习惯，但不能让维护动作混进执行的成功与否。

## 10. S0 实现范围

S0 不接真实交易所。要做真的是**协议部分**：

| 项 | S0 是否实现 | 说明 |
|---|---|---|
| 租约（获取/续期/过期/抢占） | **是** | 可完全用本地文件模拟 |
| 暂存 → 校验 → 门禁 → 登记 → 别名 | **是** | 用本地假数据驱动 |
| 门禁 A 七项检查 | **是** | 假数据可构造全部失败形态 |
| 维护日志 | **是** | 格式与归属必须一次定对 |
| 上游修订检测 | **是** | 两次假采集改一行值即可 |
| `gc --derived` | 是（只做安全删除） | 不删 `Seed` / `Register` |
| 真实 HTTP 采集 | 否 | 留在 S2 |
| 限流、重试退避 | 否 | 留在 S2 |
| 交易所适配器 | 否 | 留在 S2 |

理由：协议错了，接真实数据只会把错误放大；协议对了，S2 换实现不动契约。

## 11. S0 验收点（本篇）

| # | 断言 |
|---|---|
| U1 | 两个进程同时 `acquire` 同一数据集 → 一成一败，败者 `E5002` |
| U2 | 租约过期后可被抢占，且日志记录 `previous_owner` |
| U3 | `acquire` 成功后别名未移动（`pins/` 内容不变） |
| U4 | `publish` 中途 kill → 别名仍指向旧版本，新版本或不存在或不完整但**不可用** |
| U5 | 校验和不符 → 版本保留、`gate_a.passed=false`、别名不动、退出码 4 |
| U6 | 部分成功 → `missing_ranges` 非空、`passed=false`、退出码 4 |
| U7 | 同内容重复 `publish` → 版本目录不变、`acquired_at` 不变、只增一条日志 |
| U8 | 上游修订 → 新版本、旧版本仍可读、日志含 `revision_detected` |
| U9 | 别名文件写入是原子的：并发读永不读到半个 JSON |
| U10 | 维护日志不出现在任何 `Ticket/` 目录；执行侧可按 `pin.version` 反查 |
| U11 | 编译期缺数据 → `E4001`，且 `staging/` 与 `seeds/` 均无新增 |
| U12 | `gc --derived` 不删除任何 `Seed` 与 `Register` 条目 |
| U13 | 维护日志的 `detail` 不含凭据（模式扫描） |
| U14 | 执行期任何层尝试调用 `supply` 命令 → `E4006` |
