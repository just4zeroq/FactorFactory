# 01 · 底层能力层

> 本篇定义「给什么算什么」的那一层：统一调用契约、能力清单、名字空间，以及能力为什么必须无权。

---

## 1. 定位：算得对，但不做决定

能力层是一组**无状态、按名字调用的计算服务**。编排层决定按什么顺序、按什么口径跑；能力层只负责把一步算对。

四条无权，靠**函数签名**保证，不靠约定：

| 能力签名里没有 | 归属 | 若放进来的后果 |
|---|---|---|
| 配置对象 | 意图层 | 能力能自己查默认值、自己选口径，冻结方案形同虚设 |
| 账本 / 试验计数句柄 | 编排层 | 算法可以少报、漏报、清零计数 |
| 结论 / 显著性判定出口 | 唯一裁判 | 判据被分散打折，出现多个「通过」标准 |
| 别名 / 「最新」解析入口 | 运行时 | 同一次执行的不同工位可能读到不同数据版本 |

另外三条：能力**不读配置文件、不写账本或共享仓、不产结论**；不认「最新」；不自选口径。以前靠「声明禁止自判显著性」来约束，现在靠「签名里根本没有这个入口」来约束，更硬。

「不自选口径」的准确含义是：**口径可以进来，但只能以只读、受限子集、由编译器填好的形式进来**（见 §2 的 `policy_view`）。能力读不到配置树，读不到别的子块，也改不了任何一个值——这三件事合起来，才是「不自选」。

能力可以被流水线之外的只读诊断通道调用，但那条通道标只读，产物不进正式结论链。

---

## 2. 统一调用契约

所有能力的主接口形状完全一致：

```
run(call) -> 产物
```

调用单 = 身份 + **四个输入通道** + 子调用。身份是工位、实现名、版本三个字段；四个输入通道缺一不可：

| 通道 | 内容 | 谁生成 | 进 `call_digest` |
|---|---|---|---|
| `impl` / `version` | 编译期解析出的实现标识与显式版本 | 编译器 | 是 |
| `params` | 已按该实现 schema 校验的参数，全量展开、无占位 | 编译器 | 是（经 `params_digest`） |
| `inputs` | 精确的上游产物引用与共享事实引用，有序 | 编排层 | 是 |
| `policy_view` | 冻结口径的**具体取值**（不是哈希） | 编译器 | 是（经 `policy_digest`） |
| `runtime_facts` | 执行期确定、但**会改变结论**的事实：试验计数、揭示状态、审核状态 | 编排层 | **是** |
| `composed` | 已构造好的子调用单，有序（见 §2.2） | 编排层 | 是（经各自 `call_digest`） |

此前只有一个 `policy_digest`（口径的哈希）是不够的：能力拿不到口径的值就必须从 `params` 里再写一遍，于是同一份口径出现两个来源；而 `n_trials`、揭示状态这类执行期事实既不能当参数（否则可以填小），也不能当配置（否则可以预置），必须**由编排层注入且进指纹**。

三条分工原则：

- **`params` 只装这个实现自己的选择**。凡属 `caliber`（跨度、入场价、成本档、年化、构造约束）的字段，一律从 `policy_view` 读，写进 `params` 即编译失败（C20）。这是口径不可能漂移的结构保证。
- **`runtime_facts` 进指纹**。`n_trials` 变了判据就变了，缓存必须失效；若它不进指纹，同一份输入会命中一份过期结论。
- **`policy_view` 是只读投影**，只含本能力声明会读的子集，能力看不到与自己无关的口径。

**调用单整体进指纹**：实现名 + 版本 + 参数 + 输入引用 + 口径取值 + 执行期事实 + 子调用。换实现、改参数、换数据版本、换计数快照都会产生不同指纹。

每个能力配一个元信息接口：

```
describe() -> { impl, version, param_schema, deterministic, needs_seed,
                cacheable, side_effect, composes, policy_reads }
```

`param_schema` 逐字段声明类型、范围、是否必填、默认值、参数类别（构成性 / 操作性）。`policy_reads` 声明本能力会读 `caliber` 的哪些子块，编译期据此组装 `policy_view`——**读什么由声明决定，不是由实现运行时决定**。

### 2.1 拟合类能力：两个调用，不是一个

**有状态能力必须拆成两次调用**，由编排层分别构造调用单：

```
search.fit(call_fit)        -> FittedState       # inputs 只含搜索区间
search.generate(call_gen)   -> CandidateSet      # inputs 含 fit 产物引用
```

拆开不是为了好看，是为了让「拟合有没有越界到评估窗口」变成**可验证的结构事实**：`call_fit.inputs` 里根本不包含评估区间的引用，越界在类型上就不成立。合成一次调用后，越界只能靠实现自觉。

**`call_fit` 比 `call_gen` 多一个通道**：`runtime_facts` 之外，编排层还为它注入一个 `fitness` 闭包（调同一 `evaluate`、只读搜索区间、每次调用登记一次试验）。遗传规划与强化学习靠它在拟合阶段进化——没有这个通道，它们要么退化成纯随机生成，要么自己 `import` 求值器绕过口径校验。`call_gen` 里没有这个通道，因此生成阶段连评估入口都不存在。详见 `02-mining-interface.md` §2.1 与 §2.2。

`FittedState` 落盘为本次工位产物的一部分，带自己的引用与指纹，作为 `call_gen.inputs` 的一项；两次调用单共同进入本工位的 `parcel_digest`。

### 2.2 子调用：能力可以组合，但只能按声明组合

有些能力天然要调别的能力：证据要调构造与成本，组合要调合成、构造、成本，认证要调成本。这不是「能力互相依赖」的坏味道，而是**同一份口径被多处使用的正常形态**——问题只在于谁有权构造那个内层调用。

| 规则 | 内容 | 防住什么 |
|---|---|---|
| **声明组合** | `describe().composes` 列出会调用的能力名，编译期校验它们是同一 `caliber` 下的合法组合 | 实现临时起意去调一个没声明的能力 |
| **编排层构造** | 子调用单由编译器/执行器预先构造，作为 `call.composed` 传入；实现只负责 `run(call.composed[i])` | 能力自己拼参数、自己换口径 |
| **深度受限** | 组合深度 ≤ 2；`backtest`、`evaluate` 与 `read` 是叶子，不得再组合 | 出现一条隐式的能力依赖图 |
| **失败不换码** | 子调用失败原样上抛，父调用失败，错误码与上下文保留 | 底层 `E4002` 被包装成 `E3004`，排查退化 |
| **指纹包含子调用** | 每个子调用的 `call_digest` 进入父调用单 | 换了成本实现，父产物却复用旧缓存 |

于是「证据层与回测层各写一遍成本逻辑」这条漂移路径被结构消掉了：它们调的是**同一个子调用**，构造参数来自同一个 `caliber` 块，指纹逐项相同。

### 2.3 工位内中间产物不跨工位

`read` 产出的字段流、`align` 产出的面板中间态，都是**工位内中间产物**：它们在实现内部流转，不落成 `Parcel`，不进入工位间的依赖图。

跨工位的只有 `Parcel`。这条区分解决了一个容易含混的问题：`read` 没有自己的工位，也不需要——它是 Panel 工位声明的一个子能力，产物在 Panel 落盘时被吸收成 `PanelParcel` 的一部分。

## 3. 名字 → 实现目录

编排时每个模块只写**名字 + 参数**。名字在编译期查一张目录表，解析成 `实现@版本`；参数按该实现自带的 schema 逐项校验。编排层不知道实现细节，能力层不知道自己被谁调用。

| 规则 | 内容 | 防住什么 |
|---|---|---|
| 名字编译期解析 | 名字不在目录中、拼写错误 → 编译失败 | 写错算法名却悄悄跑了另一个实现 |
| 参数按 schema 校验 | 出现 schema 之外的字段、缺必填、类型不符 → 编译失败 | 参数名拼错被忽略，实际用了默认值 |
| 调用单整体进指纹 | 见本篇 §2 | 换实现却复用旧缓存 |
| 名字空间分档 | 见本篇 §4 | 每层都长出可选项，配置组合变成隐式模型选择 |

裁判是唯一例外：只有一个实现，**不进目录表，配置里不能指定另一个名字**，也不能注入宽松默认；缺失即拒绝编译与执行。

数据类名字还有一层特殊性：`exchange` 与 `datasets` 不是运行期下载指令，而是编译期声明「使用哪一份已发布的事实版本」。名字与字段清单被解析成精确版本引用并做只读适用性校验；缺失或未通过门禁 → 编译失败且不创建执行。

这里**没有协议类、能力声明、能力协商、hook 组合或插件容器**。八步顺序固定，调用单固定，缺什么看函数签名就知道；运行时热加载与动态层序已明确不做，插件框架的绝大部分价值就不存在了。

## 4. 四档名字空间

「这一步要不要支持多种算法」，等价于问「配置里这个名字的集合有多大」。

| 档 | 集合 | 能做什么 | 出现在哪 |
|---|---|---|---|
| **开放** | 可增长 | 登记新名字、新增实现 | 挖掘算法、内置因子清单（第 4 步） |
| **封闭多选** | 有限且固定，成员 > 1 | 配置里选一个，**不许加名字**；构造与成本在 `caliber` 里选，工位不可覆盖 | 合成器（第 7 步）、构造与成本（第 5 / 6 / 7 / 8 步共享） |
| **单实现** | 恰好 1 | 只能同名字下升版本 | 第 1 / 2 / 3 / 5 / 8 步的全部能力 |
| **唯一且不可配** | 恰好 1，且配置里不出现 | 只能随实现整体升级 | 裁决（第 6 步） |

三处容易误判：

- **交易所名不是算法名**。它是参数值：所有交易所走同一个 `read` 实现，交易所差异压在供给维护链的适配器里，编排层看不到。这是「参数值多」而不是「算法多」。
- **内部组件不是可选项**。面板里的对齐 → 因果探针 → 质量门禁，是固定串联的内部步骤，配置单里根本不出现；组合里的正交化、约束投影、资金费结算同理。把它们列成「可选能力名」会让人误以为每层都要做插件框架。
- **看起来最该开放的，恰恰不能开放**。证据层的零分布、显著性校正、指标计算确实各有多种算法，但可随手切换就等于绕过判据；裁决层更是连第二个实现都不允许。变体只能走只读诊断通道，不进正式结论链。

封闭多选档里的名字虽然能选，但都属于**构成性口径**：换一个就是新计划 + 新试验族，不复用旧计数。它的价值是对照与升级，不是随手调参。

## 5. 能力清单

「服务工位」列写的是**对外归属**：能力可以被工位直接调用，也可以被另一个能力按 `composes` 组合调用。括号里的 `子` 表示它是某个工位的子能力，不单独落 `Parcel`。

| 能力 | 服务工位 | 名字空间 | 主接口 | 组合 | 参数类别 | 副作用 | 可缓存 |
|---|---|---|---|---|---|---|---|
| `read` 事实读取 | Panel（子） | 单实现 | `read(refs, spec) → 字段流` | 叶子 | 构成性 | pure | 是 |
| `boundary` 边界构建 | Boundary | 单实现 | `build(refs, params) → 边界` | 叶子 | 构成性 | repeatable | 是 |
| `align` 面板对齐 | Panel（子） | 单实现 | `align(字段流, params) → 面板` | 叶子 | 操作性 | repeatable | 是 |
| `label` 标签生成 | Target | 单实现 | `label(面板, params) → 标签` | 叶子 | 构成性 | pure | 是 |
| `search` 候选生成 | Search | **开放** | 见 `02-mining-interface.md` | 叶子 | 构成性 | **append_only** | 否 |
| `evaluate` 表达式求值 | Evidence / Certify（子） | 单实现 | `evaluate(载荷, 面板, 口径) → 暴露` | 叶子 | 构成性 | pure | 是 |
| `observe` 证据采集 | Evidence | 单实现 | `observe(候选, 暴露, 标签, 口径) → 观测` | `allocate`、`backtest` | 构成性 | pure | 是 |
| `verdict` 裁决 | Verdict | **唯一不可配** | `verdict(观测, 计数, 判据) → 结论` | 叶子 | 构成性 | **append_only** | 否 |
| `combine` 合成 | Portfolio | 封闭多选 | `combine(暴露, 域, params) → 合成分数` | 叶子 | 构成性 | repeatable | 是 |
| `allocate` 持仓构造 | Evidence / Portfolio / Certify | 封闭多选 | `allocate(分数, 掩码, 分层, 口径) → 持仓` | 叶子 | 构成性 | repeatable | 是 |
| `backtest` 回测 | 5 / 6 / 7 / 8 | 封闭多选 | `backtest(持仓, 价格, 资金费, 分层, 口径, detail) → 账本 + 指标` | 叶子 | 构成性 | pure | 是 |
| `certify` 认证 | Certify | 单实现 | `certify(料包, 参数) → 报告` | `evaluate`、`allocate`、`backtest` | 构成性 | repeatable | 否 |

`backtest` 有一个 `detail: enum{summary, full}` 参数：`summary` 只交净表现摘要（判据用），`full` 另交逐笔成交、现金账本、多空分账、回撤区间与分资产归因。**两档来自同一份账本**，不是两次计算——`summary` 是对账本的聚合，不是对账本的近似。这条是 I12 唯一可能的落地方式。

`evaluate` 是表达式 → 横截面暴露的唯一实现。它此前被隐含在 `observe` 内部，导致 `combine` 与 `certify` 各自再算一遍暴露，三处若求值语义不同（NaN 传播、tie 策略、除零约定）就是 C20 管不到的口径漂移。求值内核用 **qweave**（Rust DAG，自带公共子表达式复用与节点级并行），本系统只自研算子白名单、JSON AST → 表达式的构造器、跨调用缓存键。候选的规范形式是 **JSON AST 而非字符串**：字符串语法归各算法自己，见 `02-mining-interface.md` §6。组件细节见 `07-components.md` §4。

`append_only` 两项由编排层代写全局账本：能力本身只交出候选或观测，**没有写账本的接口**。

`allocate` 与 `backtest` 被三到四处复用，且参数全部来自 `caliber`，因此**任何工位都无法自带一份构造或成本参数**。这条是「同一口径」这句话唯一可能的落地方式，详见 `06-evaluation.md`。

## 6. 回测：一个引擎，两档输出，四个调用点

「回测」在这套设计里不是一步，是**同一个引擎被四处调用**：

| 调用点 | 用它做什么 | 档 |
|---|---|---|
| 第 5 步 证据 | 单因子按同一构造方式建仓、算换手、扣成本，给每个候选一个净收益 | `summary` |
| 第 6 步 裁决 | 判断「净成本后到底能不能交易」 | 读第 5 步产物 |
| 第 7 步 组合 | 合成分数按同一构造方式建仓，带约束跑完整回测 | `full` |
| 第 8 步 认证 | 在没参与搜索的新数据上用同一套判据再算一遍 | `summary` |

因此不设独立回测工位：独立工位意味着证据层和回测层各写一遍构造与成本逻辑，是口径漂移的温床。一处实现、四个调用点、一份冻结口径，才是结构上消掉漂移的办法。

**`backtest` 是真正的回测引擎，不是净收益计算器**。它的内部结构只有一条：

```
权重 ──▶ 成交模拟 ──▶ Ledger（唯一真相） ──┬──▶ aggregate(summary) → 净表现摘要
                                          └──▶ aggregate(full)    → 逐笔 + 账本 + 归因
```

`Ledger` 逐行是 `{t, asset, target_w, actual_w, fill_qty, fill_px, fee, slippage, funding}`。两档都是对**同一份账本**做聚合，因此「判据用的净收益」与「报告里的净收益」在构造上就是同一个数。**禁止为 `summary` 另写一条向量化捷径**：两套成交逻辑就是两套口径，I12 当场破裂。

实测支撑（`07-components.md` §3.1）：20 资产 × 1187 bar 的一次完整回测 0.388 秒（含 1700 笔成交、56 项指标）。200 个候选约 78 秒，不需要捷径。

杠杆与保证金属于口径，从 `caliber.net` 读：`max_leverage`、`initial_margin`、`maintenance_margin`、`liquidation_buffer`。声明了杠杆却请求 `detail=summary` 时，聚合必须走完整账本路径——捷径的无路径依赖前提不成立，由编译期校验拦下。

**单因子与组合的差异只允许是「成员数」**（`06-evaluation.md` §2）：同一个 `allocate`、同一个 `backtest`、同一组 `caliber` 参数。这条比「四项参数一致」更硬——它把「判据用的策略」和「部署的策略」变成同一个函数。

想单独换成本模型做敏感性分析，走**能力级只读诊断通道**，不拉长主链、不产生可发布结论。

以下量必须在 `caliber` 块里各有一个权威值，所有调用点只读：标签跨度与再平衡周期、入场价口径、成本档位与扣减方式、资金费结算周期、年化基准、有效截面宽度下限、构造约束、杠杆与保证金。**判据**：若裁决阶段认为信号「净成本后可交易」，而组合阶段用另一套构造或成本假设把它算成亏损，就是口径被违反；这类不一致必须在编译期拦下（C20），而不是在报告里附一句提醒。

## 7. 能力升级规则

除两个开放名字空间外，能力只允许升级，不允许新增名字：

| 步骤 | 要求 |
|---|---|
| 版本 +1 | `实现@vN → @v(N+1)` 显式发生，名字不变、接口不变 |
| 对照 | 若数值结果改变，必须给出变更前后对照，不能只说「优化了」 |
| 失效 | 该能力及其全部下游产物标 `stale`；旧执行仍按冻结版本可复现 |
| 口径判定 | 触及构成性口径的升级，**按新实验办**：新计划 + 新试验族，不复用旧计数 |
| 缓存 | 调用单含版本，升级自动 miss，无需手清缓存 |

最怕的不是升级本身，是「修了个 bug，历史结论被静默改写而记录里毫无痕迹」。版本号、对照、失效标记三样缺一不可。

## 8. 反模式

| 反模式 | 为什么危险 |
|---|---|
| 能力内部读配置或查默认值 | 冻结方案失去意义，运行期出现第二套口径 |
| 能力签名里塞进评估器或判定出口 | 判据分散，出现多个「通过」标准 |
| 算法自己写试验计数 | 计数可被少报，多重检验门槛失真 |
| 把内部固定组件列成可选能力名 | 每层长出可选项，配置组合变成隐式模型选择 |
| 把交易所名当实现名 | 参数值被误当成算法，凭空多出一层抽象 |
| 封闭档随意加新名字 | 口径改动被包装成「升级」，绕过新实验约束 |
| 证据层 / 认证层开放多种判据算法 | 挑一个最好看的，等于免费重试 |
| 升级后不标失效、不做对照 | 历史结论被静默改写 |
| 把口径写进 `params` 而不是从 `policy_view` 读 | 同一份口径出现两个来源，两份迟早不一致 |
| 能力自己构造子调用 | 可以绕过声明去调一个更宽松的零分布或更便宜的成本 |
| 单因子评估与组合评估用不同构造 | 判据用的策略不是部署的策略，可交易结论无效 |
