# 02 · 挖掘算法统一接口

> 本篇定义第 4 步 Search 的算法抽象：四个方法、一份统一候选结构、编译期专属校验，以及多个算法如何共存而不刷结论。

---

## 1. 为什么只有它需要抽象

其余能力是「一个名字 = 一个实现」，升级只是同名字下换版本。找因子不同，有两个理由必须抽象：

1. **名字会一直增加**：符号搜索、随机表达式、遗传规划、神经网络、强化学习、模板枚举都可以成为候选来源，这是系统长期演进的主入口。
2. **输出形状不一样**：有的产出表达式，有的产出树，有的产出训练好的模型。若各交各的，证据层就得为每个算法写一套适配，等于把算法差异扩散到整条链。

抽象的目标因此很窄：**把「怎么找」统一成「交出一份标准候选集合」**，之后所有步骤只认这一份结构。算法仍然可以自由实现，但边界必须一致。

> 编排层只需要写 `algorithm: <名字>` 加该算法的参数。它不知道算法内部怎么搜索，也不需要知道。

## 2. 四个方法

```
describe()                                   -> AlgorithmSpec     必选
fit(ctx, params, seed)                       -> FittedState       stateful 时必选
generate(view, params, seed, fitted_state)   -> CandidateSet      必选
lineage(candidate)                          -> Lineage           必选
```

| 方法 | 谁调用 | 约束 |
|---|---|---|
| `describe()` | 编译器 | 纯静态，不触碰数据；返回名字、版本、参数定义与能力声明 |
| `fit()` | 编排层（仅 `stateful=True`） | 只能使用 `ctx.view.mine_slice`；可经 `ctx.fitness` 取适应度（§2.1）；产出必须可序列化、可重建 |
| `generate()` | 编排层 | 唯一允许产出候选集合的出口；不得评估、筛选、判定 |
| `lineage()` | 编排层 / 认证段 | 给定候选返回父代与算子，用于血缘、去重与审计 |

`fit` 收 `ctx` 而 `generate` 收 `view`，这个不对称是故意的：**只有拟合阶段才允许有反馈通道**，生成阶段连通道都不存在。

两种调用时序，**都由编排层发起两次独立调用**：

```
stateful = False :  describe → generate(call_gen)
stateful = True  :  describe → fit(call_fit) → 落盘 FittedState
                             → generate(call_gen, inputs 含 fitted_state_ref)
```

`call_fit` 与 `call_gen` 是两张独立的调用单，各有自己的 `call_digest`，共同进入本工位的 `parcel_digest`。

**为什么必须拆成两张单子**：`call_fit.inputs` 里**根本不包含评估区间的引用**，因此「拟合越界到评估窗口」在类型上就不成立；合成一次调用后，越界只能靠实现自觉。这是 `fit_window=mine_only` 从「声明」变成「可验证事实」的唯一办法。

`FittedState` 不可重建时，`generate` 不得降级重跑：直接失败。降级重跑会让同一次执行出现两份拟合结果，而计数只记一次。

---

### 2.1 适应度通道：有反馈的范式必须在 `fit` 内评估

`generate()` 不得评估，但遗传规划与强化学习的本质就是「评估 → 选择 → 再生成」。这不是矛盾，而是分工：

> **反馈只能发生在 `fit()` 里；`generate()` 只吐最终种群。**

因此 `fit` 多拿一个通道：

```
fit(ctx, params, seed) -> FittedState
ctx = { view, params, seed, rng, fitness }
fitness(payload) -> float | tuple[float, ...]
```

| 约束 | 内容 |
|---|---|
| 输入范围 | `fitness` 只能读到 `view.mine_slice` 内的面板与标签；**测试段与保留窗口不在 `view` 里，因此结构上取不到** |
| 求值口径 | 必须走**与 Evidence 工位同一个 `evaluate` 实现、同一版本、同一 `nan_policy`**；编排层注入，算法无法替换 |
| 返回值 | 标量（单目标）或小向量（多目标：绝对值 RankIC、换手、复杂度、增量相关）。**不含 p 值、不含成本调整后收益、不含任何判据** |
| 产物 | 不得写 `Parcel`、不得进任何可发布产物；只活在 `FittedState` 内部 |
| 计数 | 每次调用即一次试验，由编排层在闭包内登记（见 §2.2） |
| 可替换性 | 编译期用确定性桩（返回常数）替换 `fitness`，用于校验算法不依赖返回值大小也能跑完 |

**为什么必须有这条通道**：没有它只有两种结局——要么 GP 退化成纯随机生成（那就不是 GP），要么实现自己 `import` 求值器，绕过口径校验，回到「三处算子语义不一致」的老问题。

**为什么必须受限**：如果 `fitness` 能返回 p 值或成本调整后收益，算法就会朝「更容易过闸门」的方向搜索。这是**搜索空间污染**——比数据泄漏更难发现，因为每一步都合法，只是目标被换掉了。

### 2.2 试验计数：`fit` 内的评估也是试验

GP 的 300 个体 × 30 代 = 9000 次评估，是**真实的 9000 次尝试**。若只按最终 `CandidateSet.count`（300）登记，`n_trials` 被低估 30 倍，DSR 门槛随之下调，晋升门槛形同虚设。

| 规则 | 内容 |
|---|---|
| 计数单位 | **去重后的 `candidate_id`**，与它出现在 `fit` 内还是 `CandidateSet` 里无关 |
| 重复评估 | 同一表达式被精英保留反复评估 → 只计一次 |
| 写入者 | 编排层。`fitness` 是编排层构造的闭包，登记发生在闭包内，**算法手里没有账本句柄** |
| 合并 | `fit` 内评估过的候选若又进入 `CandidateSet`，不二次计数 |
| 不得少记 | 算法无法隐藏评估：不调 `fitness` 就得不到适应度，进化跑不下去 |

这条的代价要说清：`n_trials` 从 300 量级涨到数千量级，DSR 门槛按 `√(2 ln n)` 上升约 1.3 倍（255 → 5000 对应门槛约 1.53 → 约 2.0）。**这是诚实计数的必然结果，不是需要绕过的障碍**——之前「闸门不可信」的根源之一就是计数被系统性压低。

反过来说：任何试图「只登记最终种群」的实现，都等于在门槛上作弊，必须视为实现缺陷而不是性能优化。

## 3. AlgorithmSpec（`describe()` 的返回）

| 字段 | 说明 | 编译期用途 |
|---|---|---|
| `name` / `version` | 名字与显式版本 | 查目录、进调用单与指纹 |
| `param_schema` | 逐字段声明类型、范围、必填、默认值、参数类别 | C14；生成 `flow explain` 的参数表 |
| `deterministic` | 同一种子是否可复现 | 非确定性实现不得作为默认 |
| `needs_seed` | 是否需要随机源 | 编排层按名字派生种子 |
| `stateful` | 是否需要单独拟合阶段 | 决定调用时序与 C17 |
| `needs_fitness` | 拟合阶段是否需要适应度通道 | 声明 `false` 而 `fit` 内调用 `ctx.fitness` → 运行期失败；声明 `true` 而 `stateful=false` → 编译失败（只有拟合阶段才有通道） |
| `fitness_objectives` | 多目标的组成，如 `["abs_rank_ic", "turnover", "complexity"]` | 编译期与 `caliber` 的换手定义比对；目标集合变了即新试验族 |
| `fit_window` | **唯一允许值 `mine_only`** | C17；禁止拟合越界 |
| `output_kind` | `expression` / `model_ref` | 决定落盘前跑语法沙箱还是推理依赖检查 |
| `required_fields` | 算法会用到的字段清单 | C15：与已固化的供给版本比对 |
| `operator_whitelist` | 表达式类算法声明的可用算子 | C16：与全局白名单取交集 |
| `max_candidates` | 单次产出的候选数硬上限 | C14：多算法配额总和校验 |
| `budget_group` | 默认 `inherit`，继承计划里的试验族 | 禁止算法自建族或分账 |

`describe()` 是**声明**，不是运行时兜底：它必须在编译期就能完整读到，不能依赖读数据后才确定。

## 4. MarketView：算法唯一能看到的输入

| 字段 | 说明 |
|---|---|
| `panel_ref` / `label_ref` | 精确的上游产物引用，只读 |
| `mine_slice` | 允许搜索与拟合的时间区间 |
| `observable_mask` / `tradable_mask` | 逐时点两张掩码 |
| `field_manifest` | 本次实际可用字段清单及其版本 |
| `family` | 编译期给定的试验族，只读 |
| `seed` | 编排层按算法名确定性派生的种子 |

**明确不含**：样本外与保留窗口、任何评估指标、判据阈值、账本句柄、配置对象、文件系统写权限、网络访问、别名解析入口、`caliber`。

这是一份**只读投影**。算法拿不到评估窗口，也拿不到判据，因此「在生成阶段偷偷挑表现好的候选」在结构上就不可能。

**`fitness` 为什么在 `ctx` 里而不在 `view` 里**：`view` 是纯数据投影（可序列化、可做指纹），`fitness` 是受控函数（有副作用：登记试验计数）。把函数塞进数据对象，会让 `view` 无法参与指纹，也会让「这个对象可以安全落盘/传参」这条前提失效。两者分开，还带来一个好处：`generate` 只收 `view`，因此在生成阶段连调用通道都拿不到。

## 5. FittedState（仅有状态算法）

| 约束 | 理由 |
|---|---|
| 可序列化、可落盘 | 跨工位只传不可变产物，不传活对象 |
| 可由 `panel_ref + params + seed` 重建 | 单步重放与复现的前提 |
| 不含连接句柄、生成器、内存视图 | 重建失败必须显式失败，不能降级 |
| 拟合只读 `view.mine_slice` | 编译期校验 `fit_window=mine_only` |
| 引用进入候选料包与调用单指纹 | 换拟合结果即缓存失效 |

`output_kind = model_ref` 时，候选载荷是**可落盘的推理产物引用**，不是模型实例。证据层按引用加载并计算暴露，不需要知道算法内部是什么网络。

## 6. 统一候选结构

这是整篇最关键的契约：所有算法、所有内置因子，最终都归一成同一种 `Candidate`。

| 字段 | 说明 |
|---|---|
| `candidate_id` | **内容身份**：`H(payload + required_fields)`，与谁生成它无关 |
| `source` | `algorithm` / `prior` |
| `generator` | `name@version`，**仅谱系元数据**：不参与 `candidate_id`，不分池、不分族、不分账 |
| `payload` | `expression`（**规范化 JSON AST**，唯一规范形式，可哈希）或 `model_ref`（可落盘引用） |
| `required_fields` | 该候选计算时需要的字段 |
| `parents` | 父代 `candidate_id` 列表 |
| `operators` | 用到的算子清单 |
| `available_from` | **执行期 as-of 时点**：由编译期固化的数据末端确定，不是墙钟时间 |
| `params_snapshot` / `seed` | 生成时的参数与种子快照，**仅谱系元数据** |

**`payload` 为什么用 JSON AST 而不是字符串**：字符串表达式的语法由各算法自己决定（GP 产出的串、LLM 产出的串、模板枚举产出的串写法可能不同），让求值层去解析所有语法，等于把算法差异搬进 `evaluate`。AST 是唯一规范形式——算法负责把自己的语法转成下面这三种节点，`evaluate` 只认这一种。附带好处是 C16 白名单校验退化成一次 AST 遍历，不需要引入语法沙箱。

**节点文法（三种，闭合，无第四种）**：

| 节点 | 形状 | 说明 |
|---|---|---|
| 字段 | `{"field": "close"}` | 叶子。字段名必须在字段注册表内，且 `required_fields` 必须已经声明它 |
| 常量 | `{"const": 2}` | 叶子。**只接受有限实数**（`int` / `float`）；`bool`、`null`、字符串一律 `E1003` |
| 算子 | `{"op": "mean", "args": [<node>, ...]}` | 内部节点。`args` 长度必须等于注册表声明的 `arity` |

三条硬约束：

1. **节点键集合必须恰好是三者之一**，出现 `{"field": ..., "const": ...}` 这种混合或任何额外键（如 `{"op": "x", "args": [], "comment": "..."}`）都是 `E1003`。多一个可自由填写的键，`candidate_id` 的内容身份就被稀释了——两个「语义相同但注释不同」的表达式会被算成两个候选，`n_trials` 虚高。
2. **带参算子（`delay`/`sum`/`mean`/`std`/`max`/`min`/`delta`/`corr`/`cov`）的末位参数只能是 `{"const": int}`**，且在注册表声明的 `param_domain` 闭区间内（越界 `E1008`）。这些参数是窗口长度或滞后期数，是**计数**不是连续量：`{"field": "x"}` 当参数是 `E1003`，`{"const": 2.0}` 也是 `E1003`——允许浮点等于允许 `2` 与 `2.0` 两种等价写法，`candidate_id` 就不稳定了。`bool` 尤其要拒绝：`True` 会静默变成 `1`，把 `lag=0` 变成 `lag=1`，未来函数的入口。
3. **嵌套深度上限 64**（`E1003`）。没有上限时，一个递归生成的退化表达式能让 `evaluate` 的递归栈先于守卫崩溃，把「拒绝」变成「异常退出」。

**数值常量与整数参数的区分**：值位置的 `{"const": 0.5}` 是连续系数（合法，与 `mul`/`add` 等二元算子配合）；参数位置的 `{"const": 2}` 是计数（必须是 int）。两者形状相同、语义不同，判定依据是**位置**而非节点本身——同一个 `{"const": 2}` 在 `mul(close, {"const": 2})` 里是系数，在 `mean(close, {"const": 2})` 里是窗口长度。因此 `{"const": 2}` 与 `{"const": 2.0}` 在值位置**都合法且必须解析为同一个 `candidate_id`**（规范化为 JSON 数字的最简形式），在参数位置则只有前者合法。

**`candidate_id` 为什么不能包含生成器与种子**：跨算法去重要求「两个算法产出同一个表达式」被识别为同一个候选。若 id 里带上 `name@version + seed`，两者必然不同，去重永远不生效，`n_trials` 被系统性放大——门槛虚高，真信号被拦掉。内容身份让去重成立，也让「先验池成员与算法产出撞车」自然收敛为一条。

代价是必须显式记录来源：同一表达式由两个算法生成时，`generator` 保留两条谱系（写入 `generators` 列表），但计数只加一。**计数认的是「试了多少个不同的东西」，不是「用了几种方式试」。**

**`available_from` 为什么不能用墙钟**：它是口径的一部分（进 `domain_digest` → `policy_digest`）。若取「本次执行登记时间」，同一个计划今天跑和明天跑会得到不同的口径指纹，`AC3`（同方案两次执行一致）与单步重放逐位一致当场不成立。两种合法取值：

| 场景 | `available_from` |
|---|---|
| 本次执行产出、只在本域内使用（`local_only`） | 编译期固化的数据末端 as-of 时点 |
| 登记进全局因子库 | 首次通过裁决的真实登记时刻（那一刻它已是冻结状态） |

`CandidateSet.declared_at` 同理：它是**观测字段，不进任何指纹**。

**禁止出现的字段**：任何指标、RankIC、p 值、成本、权重、结论、状态、排序。候选一旦携带这些，就等于算法自己做了评估，证据层与裁判会被架空。

### CandidateSet

| 字段 | 说明 |
|---|---|
| `candidates` | 跨来源去重后的有序集合 |
| `family` | 只读继承编译期试验族 |
| `count` | **去重后的实测数量** |
| `dedup_digest` | 集合指纹 |
| `fitted_state_ref` | 可空 |
| `declared_at` | 登记时间 |

> **试验计数只认 `CandidateSet.count`，不认配置里声明的 `population` / `max_candidates`。**
> 算法无法少报；若实际产出超过配额上限，由 C14 在编译期与落盘前双重拦下。这条把「声明了多少次试验」和「实际做了多少次试验」分开，堵住计数失真的入口。

### Lineage

`lineage(candidate)` 返回 `{ parents, operators, generation, generator }`。它用于血缘回溯、跨算法去重、组合域的 `available_from` 判定与认证审计；任何合成分数都必须能回溯到具体成员与具体裁决记录。成员谱系不可为空。

## 7. 编译期专属校验（C13–C17）

基础校验 C1–C12 见 `04-runtime.md`；以下五条只针对算法接口，全部 fail-closed：

| # | 触发条件 | 处理 |
|---|---|---|
| **C13** | 算法名未登记、`describe()` 签名不符、四个方法缺一 | 拒绝编译 |
| **C14** | 参数出现 `param_schema` 之外的字段、类型/范围不符；多算法配额总和超计划上限；落盘时实际产出超 `max_candidates` | 拒绝编译 / 整批拒绝 |
| **C15** | `required_fields` 超出已固化供给版本的覆盖范围 | 拒绝编译；不得自动补采 |
| **C16** | `operator_whitelist` 含禁用构造（负向位移、未来算子、全期统计、跨时点未来量）或与全局白名单冲突 | 拒绝编译 |
| **C17** | `stateful=True` 但 `fit_window != mine_only`；`FittedState` 不可重建；`model_ref` 推理产物不可落盘 | 拒绝编译 |

**双保险**：候选产出之后、写入料包之前，再对每个 `payload` 跑一次检查——表达式类过语法沙箱，模型类过推理输入依赖检查。**不通过则整批拒绝**，不是丢掉几个坏候选后继续：静默丢弃会改变实际试验数，而计数已经登记。

C16 必须在编译期，不能靠运行时约定：语法沙箱要在算法开始搜索之前就知道哪些构造根本不允许被生成。

白名单的具体集合不是自拟的：它以 **qweave 0.6.2 的算子表**为基线（逐元素 / 时序窗口 / 指数平滑 / 截面四类），再减去加密场景不适用与构成前视的构造。qweave 不支持注册自定义算子，因此**新增因子只能靠表达式组合，不能新增算子语义**——这条限制要写进算法作者的接入说明（`07-components.md` §4.4）。

C17 除了编译期校验声明，还有一处**运行期结构校验**：`call_fit.inputs` 中不得出现任何落在搜索区间之外的引用；出现即 `E1016`，不等实现自己声明。这条把「拟合有没有越界」从口头约束变成一次可断言的比对。

### 7.1 多算法与两张调用单

多算法并列时，`fit` 与 `generate` 的拆法不变：每个算法各自一对调用单，`FittedState` 各自落盘，最后在 `CandidateSet` 处合并。**合并后仍只有一次计数**，且 `count` 是跨算法去重后的实测值——去重键是 `candidate_id`（内容身份），不含 `generator`。

## 8. 三条禁令的结构保证

| 禁令 | 靠什么保证 |
|---|---|
| **算法不产生证据** | `Candidate` 结构里没有指标字段；`MarketView` 里没有评估窗口、没有判据；`fitness` 只返回标量/向量，不返回 p 值或成本后收益（§2.1） |
| **算法不判显著** | 四个方法的签名里没有判据、阈值、结论出口 |
| **算法不写试验计数** | 没有账本句柄；`fitness` 是编排层构造的闭包，登记在闭包内发生；Budget 事件由编排层在 `CandidateSet` 落盘后按 `count` 代写 |

**「不评估」与「不产生证据」的区别值得单列**：有反馈的范式（GP / RL）必须在 `fit` 内评估，否则无法进化。允许它评估、但禁止它把评估结果变成证据——前者是搜索手段，后者是会误导下游的结论。这条界线靠三件事同时成立来划：评估只在 `fit` 内、只看 `mine_slice`、返回值的形状里没有结论。

因此接入一个新算法**不需要碰任何闸门、阈值或账本**。以前靠「声明式禁止」约束，现在靠签名里根本没有入口，更硬。

评估归证据层，判定归唯一裁判，计数归编排层——这三条分工不因算法种类变化。

## 9. 参数定义样例

```yaml
name: gp_symbolic
version: v2
stateful: false
output_kind: expression
required_fields: [close, volume, funding_rate]
operator_whitelist: [add, sub, mul, safe_div, ts_mean, ts_std, cs_rank]
max_candidates: 500

param_schema:
  population:       { type: int,  range: [10, 2000], required: true,  class: operational }
  generations:      { type: int,  range: [1, 500],   required: true,  class: operational }
  max_depth:        { type: int,  range: [2, 12],    required: true,  class: constitutive }
  operator_set:     { type: enum, values: [arith, rolling, cs_rank], required: true, class: constitutive }
  tournament:       { type: int,  range: [2, 16],    default: 4,      class: operational }
  parallel:         { type: int,  range: [1, 64],    default: 1,      class: operational }
```

两点说明：

- `max_depth` / `operator_set` 决定**搜索空间**，是构成性参数，改动即新试验族。
- `population` / `generations` 只影响怎么算完，属于操作性；但它们会改变实际候选数，从而改变门槛。**计数以 `CandidateSet.count` 实测为准**，所以这两项不必进口径锚点，也不会造成计数偏差。

参数类别的判据仍是那句：如果改了这个值，同一个「显著」结论可能变成不显著，它就是构成性的。

## 10. 多个算法怎么共存

配置允许 `search.algorithms` 写成列表，每个条目 `name + params`：

| 规则 | 内容 |
|---|---|
| 同一输入 | 所有算法共享同一份 `MarketView`、同一 `family`、同一 `mine_slice` |
| 种子隔离 | 种子由主种子按 `name` 确定性派生，避免算法间互相干扰又不破坏复现 |
| 合并去重 | 各自产出汇总后，按 `candidate_id` **跨算法去重**，形成一个 `CandidateSet` |
| 一次计数 | **一次 Budget 登记**，值为合并去重后的 `count` |
| 配额 | 各算法 `max_candidates` 之和不得超过计划级上限（C14） |
| 谱系 | `generator` 只是元数据，**不得按算法分池、分族、分账**，否则判据被分散打折 |

允许的是「一次跑一个」和「一次跑多个、候选汇总后统一评估判定」。

**明确禁止**：跑三个算法 → 看哪个结果好 → 只留那个汇报。那是未记账的模型选择，等于免费刷结论。若确实要做算法对比，必须整批预注册、全部计数、走同一套证据与裁决；诊断可以分别查看每个算法的产出，但诊断结果不进正式结论链。

## 11. 内置因子字典不是算法

内置因子是一份**预注册数据**，不是接口实现：

```yaml
prior_pool:
  - { name: mom20, expression: "...", required_fields: [close], declared_at: <时间> }
  - { name: funding_carry, expression: "...", required_fields: [funding_rate], declared_at: <时间> }
```

| 规则 | 内容 |
|---|---|
| 整批声明 | 一次写完，禁止「加一条跑一次、看着不好再加一条」 |
| 统一结构 | 转成 `Candidate`，`source=prior`，与算法候选一起去重 |
| 同等对待 | 过同一套语法沙箱、同一证据漏斗、同一裁决者；不因「人工写的」而免检 |
| 一次计数 | 与算法候选合并进同一次 Budget 登记 |

每加一条先验公式等于多做一次试验。用「扩充字典」的形式免费刷结论，是最容易忽略的统计事故。

## 12. 接入新算法四步

1. **实现四个方法**（`stateful` 才需 `fit`），遵守三条禁令；产出统一 `Candidate` 结构。
2. **写 `describe()`**：`param_schema`、字段清单、算子白名单、输出类型、候选上限。
3. **登记名字**：在算法目录里加一行 `name → impl@version`。
4. **预注册**：若引入新算子、新字段或新搜索空间 → 新试验族；否则整批声明后沿用当前族，不复用旧计数。

其余七步的接口、工位顺序、闸门阈值、账本逻辑**一行都不用改**。这正是「只有两个扩展点」能成立的原因。

## 13. 算法专属验收

> 编号与陈述以 `05-contracts.md` §1（不变量）与 §4（验收）为准；本表只补本篇的检查点，不重复定义。

| # | 验收项 | 通过标准 |
|---|---|---|
| AC20 | 换算法 | 只改 `algorithm` 名字 → 调用单指纹变化、下游标 `stale`；其余七步接口与产物 schema 不变 |
| AC21 | 三条禁令 | 算法尝试写账本、评估候选、读配置或解析别名 → 编译期或运行期明确失败，不出现静默成功 |
| AC22 | 多算法共存 | 两个算法并列 → 一个 `CandidateSet`、一次 Budget、跨算法去重；`count` 等于实测去重数 |
| AC23 | 因果与配额 | 声明含禁用算子 → C16 编译失败；产出含未来字段候选 → 落盘前整批拒绝；超出 `max_candidates` → C14 拒绝 |
| AC37 | 适应度通道受限 | 在 `fit` 内尝试读测试段/保留窗口 → `view` 里不存在，直接 `AttributeError` 而非静默返回；`fitness` 返回值放进 `Candidate` 的指标字段 → `E2004` 字段白名单拒绝 |
| AC38 | 试验计数不少记 | 跑一个 `needs_fitness=true` 的算法（300 个体 × 10 代）→ `Budget` 登记值等于去重后的 `candidate_id` 数，显著大于最终 `CandidateSet.count`；把计数改成只登记最终种群 → 该验收失败 |
| AC39 | 全局随机状态不泄漏 | 同一 `seed` 连跑两次逐位一致；跑完一次 `search` 后，进程内 `random` 模块状态回到进入前的快照；并行执行两次 `search` → 明确拒绝（`E2009`），不出现互相污染的静默错误结果 |

## 14. 反模式

| 反模式 | 为什么危险 |
|---|---|
| 算法内部评估候选、自带筛选 | 证据层被架空，实际试验数不可见 |
| 候选结构里塞指标或 p 值 | 观测与裁决混在一起，判据被分散 |
| 用配置声明的数量推算试验计数 | 算法多产候选而计数不增，门槛失真 |
| 按算法分池 / 分试验族 | 每个范式各算一次显著性，判据被分散打折 |
| 跑多个算法挑最好看的 | 未记账的模型选择 |
| 内置因子逐条追加、边跑边加 | 借「字典扩充」免费重试 |
| 语法沙箱只在运行时靠约定 | 禁用构造已被生成，事故只能在事后发现 |
| 丢弃坏候选后继续 | 静默改变实际试验数，与已登记计数不符 |
| `stateful` 算法把拟合与产出合成一次调用 | 无法验证拟合是否越界到评估窗口 |
