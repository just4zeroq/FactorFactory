## D1 · 应然（抛开实现，这个模块该做什么）

`clock.py` 是注入式时钟设施。它该做的三件事（docstring:1-7）：

1. **墙钟只用于记录**：`wall()` 返回 UTC 时间，仅用于 `started_at`/`created_at` 等记录字段；**数据新鲜度判定不得读时钟**，必须用 `Pin.acquired_at` 与计划时间轴做纯函数比较。
2. **单调钟只用于计时**：`monotonic()` 用于 `seconds`/超时；冻结时钟不影响它（:28-30）。
3. **支持冻结时钟**：测试与重放时给定固定时间，所有 `wall()` 相同（:6,37-41）——这是 F8"冻结时钟下两次执行，所有记录时间字段相同、所有指纹相同"的落点。

**不变量**：业务层只拿到 `Clock` 实例，不得自行 `import time/datetime`（F1，绕过注入即 E2007）；`frozen_clock(at)` 要求带时区，归一为 UTC（:39-41）。

### 例 1 · 冻结时钟 + 单调钟（实测）

```
frozen wall() x2 = ('2026-11-16T05:00:00+00:00', '2026-11-16T05:00:00+00:00', equal=True)
frozen monotonic() x2 = (85580.265, 85580.265)     # 真单调钟，冻结不影响
naive frozen rejected: 冻结时钟必须用带时区的 datetime
Clock.wall tz aware = True
```

**解读**：
- **冻结墙钟**：`frozen_clock(2026-11-16T05:00Z)` 两次 `wall()` 逐位一致（F8 基础）。
- **单调钟独立**：冻结时钟下 `monotonic()` 仍是真实单调值（两次读数相同是因调用间隔极短，值本身来自 `time.monotonic()`，不受 frozen_at 影响）。
- **时区强制**：naive datetime 构造 `frozen_clock` 被拒；`Clock.wall()` 永远返回带 tzinfo 的 UTC。

## D4 · 代码问题（bug / 静默成功 / 口径漂移）

**已确认正确（逐条带证据）**：
1. **墙钟 UTC + 带时区**：`wall()` 返回 `datetime.now(timezone.utc)` 或 frozen_at（:22-26），实测 tz aware。
2. **单调钟独立**：`monotonic()` 直接 `time.monotonic()`（:28-30），不受冻结影响（实测）。
3. **冻结重放确定**：`frozen_clock` 两次 wall() 逐位一致（实测，F8）。
4. **时区强制**：naive datetime 构造 frozen_clock 被拒（实测）。
5. **新鲜度不依赖墙钟**：docstring:3-4 明确"数据新鲜度判定不得读时钟，用 Pin.acquired_at 与计划时间轴纯函数比较"——避免"墙钟漂移导致同一份数据时而新鲜时而不新鲜"。
6. **实例级隔离**：`Clock` 是 frozen dataclass，每个 Facilities 持自己的实例（facilities/__init__.py:83），无模块级单例污染。

**发现的问题**：
- K-2（ValueError vs FlowError）、K-3（`today()` 命名"交易日"易误导）、K-4（单调钟冻结语义）——均 P2 说明性，无 P0/P1 级 bug。
