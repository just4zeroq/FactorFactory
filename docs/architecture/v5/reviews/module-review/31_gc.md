## D1 · 应然（抛开实现，这个模块该做什么）

GC 是 **facts 区的引用计数回收器**，回答"哪些内容寻址对象无人引用、可安全删除"。职责边界：

1. **真相是引用，不是目录**：对象完整 digest 是否出现在任何一处真相文本里——`runs/**` 的 parcel/payload/frozen/trace、`db/*.jsonl` 四类登记、`catalog/factors.jsonl`、`parcels/**` depot 侧引用（`:3-9`）。
2. **一层扫描即全部可达性**：内容寻址对象之间无指针，parcel 里存最终 digest 而非对象图，所以不做可达性分析（`:11-12`）。
3. **两个安全边界**（`:14-18`）：
   - `plan_gc` 只读出清单，先看再确认（默认不删）；
   - 只扫 `facts/` 的 FACT_KINDS 类别目录，只删 `.parquet`/`.json`，不递归删其它区；删前再核一次引用集，避免扫描后被新 run 引用。
4. **单一白名单**：`_KINDS = FACT_KINDS`（`:33`），与 index/fact_kind 同源，修复历史"index 漏 parcel_data 导致 GC 与索引对活对象分叉"（`:31-32` 注释）。

### 例 1：引用计数 + 回收（实测）

```
=== G GC 引用计数/回收 ===
{'对象总数': 4, '被引用': 1, '未引用': 3,
 'keep被引用': True, 'dead被引用': False,
 '实际删除数': 3, '删前': 4, '删后': 1, 'bytes_freed': 1195}
```

输入：
```
os_=ObjectStore(L)
ref_keep=os_.write_json("reports",{"keep":True})   # 写入对象 A
ref_dead=os_.write_json("reports",{"dead":True})   # 写入对象 B、C...
# 在 db/members.jsonl 写入一条含 ref_keep.digest 的登记（唯一引用）
plan=plan_gc(L); applied=apply_gc(L)
```

逐格解读：
- **对象总数=4**：probe2 前序步骤累计写入 4 个对象（含 2 个 panels parquet + 2 个 reports json）。
- **被引用=1 / 未引用=3**：`referenced_digests` 扫 `runs/parcels/db/catalog/baselines` 的文本，只发现 keep 的 digest（`keep被引用=True`、`dead被引用=False`，`:48-57`）。
- **实际删除数=3**：`apply_gc` 逐候选删前重核引用集（`:111-113`），删 3 个孤儿，bytes_freed=1195。
- **计划只读**：`plan_gc` 返回 `candidates`（按字节降序，`:87`），不删除——"先看清单再确认"落地。

### 失败路径 / 边界（代码路径 + 逻辑核对）

| 场景 | 行为 |
|---|---|
| 扫描后被新 run 引用（引用集变化） | `apply_gc` 删前重核，若 digest 仍在引用集 → 记 `skipped{reason:"referenced_now"}` 不删（`:111-113`） |
| 单个文件删除失败（OSError） | 记 `failed` 项，不中断整批（`:115-119`） |
| 非 FACT_KINDS 目录 / 非 .parquet/.json 文件 | 不扫不删（`:63-72`），不递归删其它区 |
| 文件名非 64 位 hex | `scan_objects` 跳过（`:71-72`），不误删 |

## D2 · 差距（少什么 / 多什么 / 删什么 / 补什么）

| # | 差距 | 级别 | 证据 | 判断 |
|---|---|---|---|---|
| G-1 | **引用判定是文本正则 `sha256:([0-9a-f]{64})`**：只要 digest 字符串出现在任何真相文本里就保留，哪怕是注释/无关字段——可能过度保留（漏回收）。 | P2（保守偏差） | `gc.py:30,48-57` | **已确认符合设计**：宁可漏删不可错删；"一层扫描"的语义就是字符串出现即活。可接受。 |
| G-2 **删前重核引用集在 `apply_gc` 开头一次性算（`refs = referenced_digests`），不是每删一个重扫**：若在 `apply_gc` 执行期间（多秒）新 run 写入引用，期间删的对象不会被重核发现。 | P2（竞态） | `gc.py:103-113` | **需确认意图**：注释说"每删一个之前重核引用集"，但实际是循环外算一次、循环内用同一 `refs`（`:104,111`）——**注释与实现有出入**。GC 应在无写入窗口运行（运维约定）。建议：要么加文件锁、要么改注释为"删前统一重核一次"。 |
| G-3 **`scan_objects` 只认文件名 stem 为 64 hex**：write_json 的对象文件名是 `<hex>.json`（stem=hex，OK）；但 sidecar `<hex>.parquet.schema.json` 的后缀是 `.json` 且 stem=`<hex>.parquet.schema`（非 64 hex）被跳过——正确，sidecar 不该单独回收，随主对象删除时残留。 | P2（残留 sidecar） | `gc.py:67-72`；objects.write_table 生成 sidecar（objects.py:147-153） | **已确认小问题**：删 parquet 主对象时，同名 `.schema.json` sidecar 未被删，成为孤儿残留。实测 G 段删除的是 write_json 对象（无 sidecar）未暴露此点。建议补删对应 sidecar。 |

**多了什么**：无冗余。`bytes_total`/`reclaimable_bytes` 等统计字段是运维决策所需。

## D4 · 代码问题（bug / 静默成功 / 口径漂移）

**已确认正确（逐条带证据）**：
1. **已实现且可用**：`plan_gc`/`apply_gc`/`scan_objects`/`referenced_digests` 全部落地（推翻"GC 未做"旧基线），实测回收 3 孤儿、保 1 引用。
2. **真相是引用**：扫 5 个区的文本（`:38-45`），字符串出现即保留——实测 keep/ dead 区分正确。
3. **引用计数边界**：只扫 FACT_KINDS（`:63`），只删 .parquet/.json（`:68`），不递归其它区。
4. **删前重核**：循环内检查 digest 仍在引用集则 skip（`:111-113`）。
5. **失败隔离**：单文件 OSError 记 failed 不中断（`:115-119`）。
6. **单一白名单**：`_KINDS = FACT_KINDS`（`:33`），与 index/fact_kind 同源，历史分叉闭合。
7. **统计充分**：`bytes_total/reclaimable_bytes/bytes_freed/remaining` 供运维判断（`:88-95,120-126`）。

**发现的问题**：
- **G-2**：注释称"每删一个之前重核引用集"，实现是循环外算一次引用集（`:104`）循环内复用（`:111`）——删期间并发写入的引用不会被发现。P2 竞态，建议加文件锁或改注释。
- **G-3**：删 parquet 主对象时残留同名 `.schema.json` sidecar。P2，建议补删。
- **无 P0/P1**。

**测试覆盖**：`test_v5_catalog_ops.py:302-314` 覆盖"保引用/标孤儿 + 登记库 GC 前后字节不变（AC53）"；`test_v5_storage.py:174-194` 钉住白名单同源。未覆盖 G-2 竞态与 G-3 sidecar 残留。
