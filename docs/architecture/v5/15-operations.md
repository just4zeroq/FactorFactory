# 15 · 运维手册（runbook）

> 本篇回答：**它坏了怎么查，以及怎么判断它坏了**。
> 生产入口是 CLI（`09-app-storage.md` §2.2），没有常驻服务，所以「运维」= 定时任务 + 结构化记录 + 一套按症状索引的处置表。

---

## 1. 日常序列与检查点

```
refresh ──▶ doctor ──▶ run ──▶ factors ──▶ promote ──▶ holdout plan / reveal
   │           │            │             │           │              │
   │           │            │             │           │              └─ 只在窗口 ready 时，且只一次
   │           │            │             │           └─ writes_ledger，需 --yes
   │           │            │             └─ 只读，看拒绝原因
   │           │            └─ writes_facts，产 Ticket
   │           └─ 11 项体检；FATAL 即中止
   └─ writes_supply，失败不中止但要记录
```

| 步 | 失败时 | 不许做的事 |
|---|---|---|
| `refresh` | 记录失败原因，继续下一步（除非 `--stale-is-fatal`） | 不许在数据未刷新时改挖矿区间「凑合跑」 |
| `doctor` | **FATAL 立即停**，不建 Ticket | 不许用 `--no-verify` 之类开关跳过 |
| `run`（旧名 `experiment`） | 退出码非零即停，保留 Ticket 目录 | 不许删掉半成品目录后重跑（账本已记账） |
| `factors` | 只读，不影响状态 | 不许拿拒绝原因去调门槛 |
| `promote` | 目标已存在一律拒绝（`--force` 也不能覆盖） | 不许手工改 `factor_db` 目录 |
| `holdout reveal` | 窗口未 ready → 退出码 4 | 不许「先揭示看看」——揭示不可逆 |

`pipeline` 把前三步串起来，产出 `pipeline_<ts>.json`（`stages` / `doctor` / `run_id` / `candidates` / `promoted` / `exit_code`）。**这份 JSON 是唯一可信的「跑过没有」证据**，不是终端输出。

## 2. 结构化记录：查故障靠字段，不靠日志文本

| 记录 | 关键字段 | 用途 |
|---|---|---|
| `Ticket` | `run_id`、`plan_digest`、`blueprint_digest`、`policy_digest`、`domain_digest` | 回答「这次用的是哪份口径」 |
| 工位记录 | `station`、`parcel_digest`、`impl@version`、`duration_ms`、`status` | 回答「哪步慢、哪步失败」 |
| `Budget` 记录 | `trial_family`、`n_trials`、`source`（delivered / fit_evaluated） | 回答「门槛是按多少次试验算的」 |
| 揭示账本 | `period_key`、`revealed_at`、`ticket_id`、`operator` | 回答「谁在什么时候看了样本外」 |
| 晋升记录 | `factor_id`、`run_id`、`gate_pass`、`promoted_at`、目标路径 | 回答「这个因子凭什么进来」 |
| 维护日志 | `exchange`、`symbol`、`timeframe`、`rows`、`checksum`、`version` | 回答「这份数据是哪次采集的」 |

三条规则：

1. **日志与产物同目录同指纹**（I16）。料包失效时，同目录的日志也不可信。
2. **凭据只存引用名**（I15）。日志、Parcel、`--json` 输出里出现 `apiKey`/`secret` 即 `E2004`。
3. **`ok` 与 `exit_code` 必须一致**（I32）。不一致说明渲染层或退出路径有 bug，按契约违反处理。

## 3. 告警阈值

| 指标 | 阈值 | 含义 | 处置 |
|---|---|---|---|
| 数据新鲜度 | 1d 数据末端滞后 > 1 bar | 采集断了或 bar 未闭合 | 见 §4-1 |
| 覆盖率 | 声明的流/资产覆盖率 < 0.95 | 面板缺列或少资产 | 见 §4-2 |
| bar 连续性 | 单资产缺口 > 2 bar | 交易所 API 分页丢失 | 见 §4-3 |
| 候选数 | 一轮 0 候选 | 搜索没产出或配额为 0 | 见 §4-5 |
| 晋升数 | 连续 3 轮 0 晋升 | 可能是判据正确，也可能是数据/口径错 | 见 §4-6，**先查原因再谈门槛** |
| DSR 通过率 | 100% 失败 | 门槛与信号量级不匹配（常见且正常） | 见 §4-6 |
| 试验计数 | 单轮 `n_trials` 突降 > 50% | 计数链断了 | 见 §4-7 |
| 存储 | 执行区增长 > 预期 1.5× | GC 未生效或缓存泄漏 | 见 §4-8 |
| 运行时长 | 单轮 > 预估 3× | 缓存全 miss 或数据量变了 | 看 `duration_ms` 分项 |

**告警不许静音**：把某个阈值调松以「减少噪音」，等于取消这条检查。要么修数据，要么改判据并记为新实验。

## 4. 故障处置表

下面按症状分小节；先看这张「哪一步坏了」的索引表，再去对应小节。判据只用结构化记录里的 `station` + `parcel_digest` + 错误码，不看终端输出。

### 4-0 按工位定位

| 工位 | 典型症状 | 先看哪个字段 | 常见根因 | 转到 |
|---|---|---|---|---|
| `Boundary` | 池子突然变小、某段全被排除 | `reason_codes` 的逐格分布 | 流动性分层窗口内成交额崩塌；新上市标的被 `not_listed` | §4-3 |
| `Panel` | 面板缺列、末端多一根 | `quality_report.unclosed_dropped`、`causal_report.violations` | 采集留下未收盘尾巴；声明的流没有文件 | §4-1 / §4-2 |
| `Target` | 有效时点比预期少很多 | `dropped_bars.by_reason` | `min_width` 与池规模不匹配；中性化后宽度不足 | §4-5 |
| `Search` | 0 候选、或候选数远低于配额 | `generators[].produced`、`count` | 配额被 `E1017` 截断；算法静默返回空集 | §4-5 |
| `Evidence` | 候选有但没有一条能进裁决 | `prefilter` 淘汰计数、`null_model_id` | 覆盖率/换手被硬拦；零分布模型不是冻结的那个 | §4-6 |
| `Verdict` | 全部 `reject`、且原因相同 | `reason_counts` 的分布 | DSR 门槛与信号量级不匹配（**正常**）；成本档过低 | §4-6 |
| `Portfolio` | 权重几乎全是 0、或只有少数标的 | `binding_constraints`、`windows_used` | 约束过紧；`eval` 窗口太短；成员可用时间把 `fit` 推后 | §4-7 |
| `Certify` | 折数不足、结论 `watch`、发布被拒 | `folds_detail` 长度、`holdout_status` | 数据长度不够切 5 折；holdout 已揭示过 | §4-8 |

这张表的用法是**倒推**：报错码告诉你哪一步失败，`parcel_digest` 告诉你它读的是哪一版上游，两者的组合唯一确定一次故障。只知道「跑失败了」而不看 `station`，会把人带到错的小节。

### 4-1 末端未闭合 / 新鲜度滞后

| 症状 | 判定 | 动作 |
|---|---|---|
| `doctor` 报末端未闭合（`E4003`） | 最后一根 bar 的窗口还没走完 | 等一个 bar 周期后重跑；**不要去手工删这根 bar** |
| 数据末端比预期晚 2 bar 以上 | 采集失败或调度没跑 | 看维护日志 `rows` 与 `checksum`；重跑 `refresh` |
| 只有某个交易所滞后 | 该交易所限频或代理不稳 | 单独 refresh 该交易所；不影响其他交易所的已发布版本 |

### 4-2 面板缺列 / 覆盖率不足

| 症状 | 判定 | 动作 |
|---|---|---|
| 声明了 `basis` 但没有文件（`E1014`） | 加密流未采集 | 补采该流，或从 `caliber` 里去掉声明（= 改配置 = 新实验） |
| 某资产整段缺 | 该合约上市晚或已下架 | 走 `boundary` 的存续判定，不要 ffill 出假数据 |
| `load_crypto_streams` 静默少一列 | V4 遗留行为（V5 必须 fail-closed，I35） | 视为缺陷，报 bug，不加 try/except |

### 4-3 数据缺口

| 症状 | 判定 | 动作 |
|---|---|---|
| 单资产中间缺 2–10 bar | 分页时交易所返回空页 | 重跑该资产的 refresh；gap filler 只允许由采集触发（`13-migration.md` §3） |
| 缺口跨月 | 采集区间配错 | 检查 `start/end` 与交易所上市时间 |
| 缺口在末端 | bar 未闭合 | 见 4-1，不要补 |

### 4-4 租约冲突 / 并发

| 症状 | 判定 | 动作 |
|---|---|---|
| `E5002` 租约冲突 | 另一个进程正在发布 | 等它结束；不要删锁文件——先确认进程真的死了 |
| 两个 `pipeline` 同时跑 | 调度配置错 | 只允许一个采集者；执行之间共享的是不可变版本，不是可写路径 |

### 4-5 零候选

| 症状 | 判定 | 动作 |
|---|---|---|
| `factors` 显示 0 候选 | GP 全灭 / LLM 全失败 / 配额为 0 | 看该轮 `Budget` 与算法记录；LLM 失败**不得静默 mock 入库**（V4 缺陷） |
| 候选有但全被粗筛拦 | 覆盖率或换手超阈 | 看 `reason_codes`；**不要为了让候选通过而放宽 `turnover_max`** |
| 候选有但全被 `E1015` 拒 | 表达式用了未注册算子 | 修算法或扩注册表（= 新试验族） |

### 4-6 零晋升 / DSR 全失败

这是**最容易被误判成故障的正常结论**。

| 症状 | 判定 | 动作 |
|---|---|---|
| 连续 N 轮 0 晋升，`n_trials` 正常 | 判据在正常工作 | 先看信号量级（净 2–4 bp/bar vs 18 bp 往返成本），再谈提升信号 |
| DSR 100% 失败 | 门槛 ≈1.4 年化 SR（71 试验），而最强朴素信号仅 0.675 | **提高信号量级，不是下调门槛** |
| `n_trials` 异常小 | 计数链断了 | 见 4-7 |
| `empirical_p` 普遍接近 1 | 零分布构造错（V4：整行置换保留资产漂移，中位 `\|t\|` 4.74 > 观测 3.46） | 改为行内跨资产置换；这是缺陷不是结论 |

**红线**：不许为了「有产出」而下调 `dsr_min` / `fdr_max`、清零 `n_trials`、缩小试验族。那不是在修系统，是在改判据。

### 4-7 试验计数异常

| 症状 | 判定 | 动作 |
|---|---|---|
| `n_trials` 等于最终种群数 | 没算 `fit` 内评估（I38） | 修计数，不加解释 |
| 重跑同一执行后 `n_trials` 翻倍 | 恢复执行重复计数（I9） | 查事件绑定；账本只能追加 |
| 换算法后 `n_trials` 不变 | 多算法未合并计数（I21） | 一次 Budget，跨算法去重 |

### 4-8 存储与 GC

| 症状 | 判定 | 动作 |
|---|---|---|
| 执行区只增不减 | GC 未跑或引用计数错 | 先 `gc --dry-run` 看会删什么，再执行 |
| 对象目录出现同名不同内容 | 内容寻址被绕过（`E5004`） | 视为契约违反，立刻停写并排查写入路径 |
| 索引损坏 | duckdb 可删重建 | 删索引重扫对象，**不要动对象与登记库** |
| 磁盘将满 | — | 先归档旧执行目录，再 GC；**不要 `rm -rf` 任何目录** |

## 5. 备份与恢复：三类存储策略完全不同

| 类 | 能否重建 | 备份频率 | 恢复方式 |
|---|---|---|---|
| **对象**（parquet，内容寻址） | 能从源数据重算 | 不备份，只备份源数据与采集日志 | 重算；digest 不变才算恢复成功 |
| **登记**（append-only jsonl） | **不能重建** | **每次写入后**（或每日至少一次，含异地副本） | 从备份恢复；**丢一条 = 丢一次试验计数 = 门槛失真** |
| **索引**（duckdb） | 能重建 | 不备份 | 删除重建 |

**恢复演练的判据**：删掉索引 → 重建 → 所有查询结果逐位一致；对象目录随机删一个 → 重算后 digest 与原值相同。这两条不通过，说明「可重建」只是说法。

## 6. GC 实操

```
gc --dry-run          # 必做：列出将删除的对象与保留原因
gc --apply            # 只有 dry-run 审视过才执行
```

规则：

1. 引用计数来自登记库，不来自目录扫描；
2. 有 `Pin` 或归档引用的对象永不回收（WQ4）；
3. `--dry-run` 输出必须包含「被谁引用」的反向链接，否则无法判断能不能删；
4. 删除只允许发生在对象与执行区，**登记库永不清空**。

## 7. 变更窗口与发布

| 变更 | 是否需要停跑 | 说明 |
|---|---|---|
| 加算子 / 加字段 | 不需要，但**换新试验族** | `operators_version` / `fields_digest` 变化 → 缓存全失效 |
| 改口径（成本、跨度、年化） | 不需要，但**新计划 + 新族** | 旧结论不得与新结论混在一个报告里 |
| 升级实现版本 | 不需要 | 旧产物标 `stale`，按原版本仍可复现 |
| 改存储布局 | **需要** | 迁移期间只允许一个写者 |
| 改判据阈值 | 不需要 | 但这是新实验，且必须在报告里显著标注 |

## 8. 不变量与验收

| 编号 | 内容 | 检查点 |
|---|---|---|
| **I50** | 「跑过没有」只由结构化记录回答，不由退出码或终端输出回答 | 每条命令都能独立给出 `ticket_id` / `run_id` / `parcel_digest` |
| **I51** | 登记库每次写入后有可用的恢复点；GC 永不触碰登记库 | 恢复演练：删索引重建一致；登记库无删除路径 |
| **I52** | 告警阈值只能通过改判据（新实验）调整，不得静默放宽 | 阈值变更记入配置历史；改阈值必须新族 |
| **AC51** | 六类故障可复现且可处置 | 数据缺口 / 末端未闭合 / 租约冲突 / 揭示已用 / 指纹失配 / 磁盘满，各有一条脚本化演练 |
| **AC52** | 零晋升不被误判为故障 | 构造「信号真实但小于成本」的面板 → 系统判 0 晋升，且报告给出量级差距 |
| **AC53** | GC 安全 | `dry-run` 与实际删除集合一致；有引用对象不被删；登记库字节数不变 |
